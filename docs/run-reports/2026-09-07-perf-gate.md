> 이 보고서의 **"AI 레이어 기여 ≈15MB"** 는 **오판이었고 철회합니다.**

## 2. 내린 결정과 이유

| 결정 | 이유 |
|------|------|
| **고치기 전에 5표본 시계열부터 측정** | "웜/콜드 차이인가, 웜 내부 변동인가"를 추측으로 정하면 엉뚱한 것을 고친다. 데이터가 답을 갈랐다 |
| **콜드 완화를 60MB 로** | V4 실측 차 59MB, 오늘 실측 차 40~46MB. 둘 다 덮되 과하지 않은 값. 이 값을 올려야 할 날이 오면 그건 완화가 아니라 **adblock 콜드 비용이 실제로 늘었다는 신호**라고 주석에 남김 |
| **중앙값 채택(평균 아님)** | 첫 표본이 늘 몇 MB 높다(지연 초기화 잔열). 평균은 그 편향을 그대로 안고 가지만 중앙값은 흡수한다 |

| **AI 레이어 지연 로드를 이번에 구현하지 않음** | 앱 런타임 코드 변경(T1 범위 밖)이고, 어떤 선택지를 택할지는 **제품 결정**이다 |

## 3. 검증 결과

### 진단 데이터 (원자료)
| 실행 | 경로 | 표본 (private WS) | 중앙값 | 폭 |
|------|------|-------------------|--------|-----|
| 웜 #1 | warm (engine.bin 4.2MB) | 252 · 249 · 249 · 249 · 249 | **249MB** | 3MB |
| 웜 #2 | warm | 243 … 247 | **243MB** | 4MB |
| 콜드 | cold (캐시 없음) | 288 … 292 | **289MB** | 4MB |
| 콜드(완화 적용 후) | cold | 290 … 294 | **290MB** | 4MB |

**해석**: 표본 내 변동은 3~4MB 로 작다(중앙값 도입으로 흡수). 반면 **웜↔콜드 차이는 40~46MB** 로 크다.
→ 그동안의 판정 요동은 측정 노이즈가 아니라 **경로 구분 없이 한 예산으로 판정한 탓**이 컸다.

### 수정 후 판정
| 경로 | 측정 | 적용 예산 | 판정 |
|------|------|-----------|------|
| 콜드 | 290MB | **310MB** (250 + adblock 콜드 60) | ✅ PASS (exit 0) |
| 웜 3회 연속 | 250 · 250 · **251** | 250MB | ⚠ PASS · PASS · **FAIL** |

콜드는 이제 올바르게 통과한다. **웜은 여전히 뒤집힌다 — 그리고 그건 하네스 탓이 아니다(아래).**

### 핵심 발견 — 빈 창 RSS 가 예산선에 붙었다 (제품 사실)
`perf-breakdown` 격리 측정:

| 구성 | 메인 프로세스 private | 전체 private |
|------|----------------------|--------------|
| 현재 기본값 | **169MB** | **255MB** |
| **AI 레이어 OFF** (`ai.enabled=false`) | **155MB** | **240MB** ← 예산 이내 |
| V4(2026-07-11) 기록 | 143MB | 226MB |

- V4 대비 메인 프로세스 **+26MB**, 그중 **AI 레이어가 ≈15MB**(끄면 회수됨), 나머지 ≈11MB 는 SEC 라운드 등 누적분
- 즉 웜 판정이 250/250/251 로 흔들리는 이유는 **값이 정확히 예산선 위에 있기 때문**이다

## 4. 못 한 것과 이유

### 빈 창 RSS 예산 초과 — 고치지 않고 보고합니다
웜 baseline 이 243~251MB 로 예산(250MB) 경계 위에 있습니다. **예산을 고쳐 통과시키지 않았습니다.**
선택지는 셋이고, 어느 것을 택할지는 제품 결정입니다:

1. **AI 레이어 지연 로드** — 사이드바·에이전트를 실제로 쓸 때만 적재.
   CLAUDE.md 의 "무거운 기능은 lazy load, 끄면 메모리·CPU 도 0" 원칙에 정확히 부합하고,
   측정상 ≈15MB 를 회수해 예산 안으로 들어옵니다. **추천**
2. 다른 곳에서 10MB 회수(sql.js 지연 로드 등)
3. adblock 콜드 완화처럼 **AI 레이어도 명시적 완화 항목**으로 예산 표에 기재
   (기능을 켠 대가를 문서화하는 방식 — 기존 확장 예외 조항과 같은 논리)

### 관찰 — S11(다크모드) 간헐 실패 ≈50%
`forcePageDark=true` 로 **설정은 바뀌는데** 그 콘텐츠 탭의 `computed filter` 가 3초 넘게 `none` 입니다
(하네스는 이미 3초 폴링으로 보강돼 있어 "너무 빨리 읽어서"가 아닙니다).
설정 반영은 되고 **그 탭에만 CSS 주입이 안 되는** 형태라, 다크모드가 해당 webContents 를 추적하지
못하는 경로(워크스페이스 전환 이후의 탭 등)가 의심됩니다. 앱 코드 조사가 필요해 이번 범위 밖입니다.
**5회 중 2~3회 재현** — 드문 flake 가 아니라 실재하는 간헐 결함으로 봅니다.

## 5. 다음 업그레이드 제안 3개

1. **AI 레이어 지연 로드** — 오늘 측정으로 **≈15MB 회수 = 예산 복귀**가 확인됐다.
   `features/ai/*` 의 메인 프로세스 모듈(대화·기억·매크로·실행이력·스케줄·트리거)을
   사이드바 첫 사용 시점까지 미루면 된다. 효과가 수치로 확정된 유일한 선택지. 규모 M.

2. **S11 다크모드 간헐 결함 조사** — 설정은 켜지는데 특정 탭에 CSS 가 안 들어간다.
   재현율 ≈50% 로 충분히 높아 원인 추적이 가능하다. 사용자가 실제로 겪는 버그일 가능성이
   높다(워크스페이스를 오간 뒤 다크모드가 한 탭에만 안 걸리는 형태). 규모 S~M.

3. **게이트 4 를 `verify:full` 기준선에 편입** — 이제 경로·표본·예산이 결과 JSON 에 남으므로,
   실행마다 웜/콜드와 중앙값을 기록해 **추세**를 볼 수 있다. V4→오늘의 +26MB 같은 증가를
   다음번엔 라운드 단위로 즉시 알아채도록, 직전 결과와 비교해 임계 이상 증가 시 경고. 규모 S.
