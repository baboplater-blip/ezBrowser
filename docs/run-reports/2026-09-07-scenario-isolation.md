## 2. 내린 결정과 이유

| 결정 | 이유 |
|------|------|
| **리로드 방식을 먼저 택함** | 이 페이지는 `<script>` 안에서 MutationObserver·핸들러를 붙인다. `innerHTML` 복원으로는 리스너가 되살아나지 않아 **리로드만이 온전한 초기화**였다 |
| **4개가 깨지자 "고쳐서 통과시키기"를 하지 않음** | A2·A3 를 자급자족으로 바꾸려면 각자 `observePage` 를 다시 하게 해야 하는데, 그러면 **"A1 이 만든 ref 가 이후에도 유효한가"** 라는 회귀 감지력이 사라진다. 지금 구조가 그걸 검증하고 있었다 |
| **되돌리고 지식을 남김** | 격리는 좋은 원칙이지만 **이 스위트에는 맞지 않는다.** 되돌린 사실과 이유를 코드에 남기지 않으면 다음 사람이 같은 실험을 반복한다 |
| 정리는 **시나리오마다, 자기가 방해받을 것만** | 임무 11의 A14 방식이 옳은 granularity 였음이 이번 실험으로 확인됐다 |

## 5. 다음 업그레이드 제안 3개

1. **메모리 페이지가 `perf-history.json` 을 읽게** (임무 9·10·11 제안 유지) — 실측값이 하드코딩이라
   시간이 지나면 낡는다. 내부 페이지용 IPC 하나 + 최신 항목 표시. 규모 S.

2. **`verify:full` 요약을 status.md 에 자동 추기** — 요약 마크다운이 이미 파일로 저장되므로,
   라운드 로그에 붙이는 것까지 스크립트화하면 **"기록 없는 검증"이 구조적으로 불가능**해진다. 규모 S.

3. **`browser://memory` 의 탭 슬립·프로세스 정보 정확도 점검** — 임무 9 에서 예산 표시는 고쳤지만
   같은 페이지의 다른 수치(탭 수·슬립 상태·프로세스별 메모리)는 아직 검증한 적이 없다.
   사용자에게 보이는 화면이므로 한 번은 실측과 대조할 가치가 있다. 규모 S~M.
