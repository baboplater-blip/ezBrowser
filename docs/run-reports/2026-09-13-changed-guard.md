# 귀환 보고서 — 문구 없는 가드(changed · urlChanged)

임무: expect 가드가 기대 문구(`text`)나 `urlContains` 를 요구해, 결과 문구를 미리 모르는 클릭 작업은 2호출이 남던 것을 "화면이 바뀌었는가 / URL 이 바뀌었는가" 로도 통과할 수 있게 한다.
등급 T1~T2 · 종결 범위 push까지 · 브랜치 `auto-dev/hygiene-sync`.

## 1. 한 일

- **`agent.ts`** — `expect{changed:true}` / `expect{urlChanged:true}` 지원. 판정은 기존 기준선(`pendingTailBase`)에 **줄 집합**(`guardLines`: 본문 줄 + 요소 종류·이름·상태, 숫자·시각만 있는 줄 제외)을 추가해 `guardDiff` 로 추가/제거 줄을 센다. `changed` 는 추가+제거 ≥ 1 또는 URL 변경이면 통과하고, **무엇이 바뀌었는지 요약**(제거 2줄·추가 3줄)을 `done` 메시지에 "(확인된 변화: …)" 로 붙인다. `urlChanged` 는 URL 이 실제로 달라졌을 때만. 변화가 없으면 실패 → 모델 재질의.
- **`page-actions.ts`** — `changed`·`urlChanged` 필드.
- 프롬프트(JSON·tool 양쪽): "결과 문구를 모르면 changed/urlChanged" + "버튼 하나만 누르는 작업은 결과를 보러 다시 관찰하지 말고 click → expect(changed) → done 을 한 응답에" 예시.
- **하네스 B6~B8**(`verify-agent-loop`): B6 변화 있음 → 1호출 + done 에 변화 요약(`-"대기" +"눌림"`) · B7 변화 없는 클릭(무동작 버튼 신설) → 실패·재질의 · B8 `navigate` + urlChanged → 1호출.

## 2. 내린 결정과 이유

- **변화 판정을 "줄 집합 차이" 로** — 글자 단위 diff 보다 단순하고, 시계·카운터처럼 숫자만 바뀌는 줄을 걸러 살아 움직이는 위젯이 거짓 통과를 만들지 않게 했다. 남은 위험(동적 광고 문구 등)은 done 메시지에 붙는 변화 요약으로 사용자가 근거를 볼 수 있게 상쇄.
- **`changed` 도 기존 제한 그대로** — 발행성·위험 동작 뒤 미보관, 후속 1개·ref 없음, 인젝션 페이지 불신.
- **프롬프트 2단계 시도 후 중단** — 지시형 + 구체 예시까지 넣었으나 모델이 쓰지 않아(아래) 더 밀어붙이지 않았다. 프롬프트로 강요할수록 결과를 안 보고 완료를 보고하는 방향이라, 안전 쪽 성향을 억지로 꺾는 것은 옳지 않다고 판단.

## 3. 검증 결과

**결정론(fake-llm)**: `verify-agent-loop` **25/25**(B6·B7·B8 신규). `korean-regex` 2/2 · `npm run verify --skip-build` 5/5 · `ai-errors` 8/8 · typecheck 0.
- **L7(탭 조작) 간헐 실패의 원인을 잡았다(하네스 결함)**: 오늘 5회 중 2회 실패. 시나리오가 시험 페이지 탭을 **인덱스 1 로 하드코딩**해, 앱이 newtab 없이 시험 탭 하나로 시작한 실행(`탭 1→2`)에서는 "전환" 이 방금 연 탭을 가리켜 두 번째 닫기도 현재 탭으로 거부됐다. 관찰문의 `[탭N]` 목록에서 ▶ 가 아닌 시험 페이지 탭을 찾아 전환하도록 수정 → 이후 2회 연속 25/25. 앞 보고서에서 "이번 변경과 무관한 간헐" 이라 적은 것은 맞았지만, 원인을 찾지 않고 넘긴 것은 잘못이었다. (초기 탭이 1개가 되는 앱 측 원인 — newtab 이 생성되지 않거나 대체되는 타이밍 — 은 미조사.)
- 함정 재발: 하네스 패치 문자열의 개행 이스케이프(역슬래시 n)가 레이어(python→.mjs)를 거치며 실제 개행이 돼 정규식이 깨졌다 → `String.fromCharCode(10)` 으로 줄을 나눠 회피(이 저장소의 기존 교훈 그대로).

**실제 claude-code 벤치(세션 모드)**:

| 실행 | T1(클릭) 호출 | T2(폼) 호출 | T3(읽기) 호출 | 작업 중앙 |
|---|---|---|---|---|
| changed 가드 + 기본 안내, 3작업 × 2회 | 2 · 2 | 3 · 3 (4스텝) | 2 · 2 | 11.5s |
| + 구체 예시 문장, T1 × 3회 | 2 · 2 · 2 | — | — | 10.5s |

- **모델이 클릭 작업에서 `changed` 가드를 한 번도 쓰지 않았다(0/5).** done 메시지가 매번 "상태가 '대기'에서 '눌림'으로 바뀐 것을 확인했습니다" 인 것으로 보아, 모델은 결과를 직접 본 뒤 보고하는 쪽을 택한다. 폼 작업은 앞 라운드처럼 문구 가드를 쓴다(이번 실행은 4스텝·3호출로 가드 1회 통과).
- 따라서 이번 라운드의 **실사용 절감 효과는 확인되지 않았다.** 기전은 동작하고 안전하지만, 효과는 모델 채택에 달려 있다.

## 4. 못 한 것과 이유

- **클릭 작업 1호출화의 실증** — 위. 모델(claude via CLI)의 성향 문제라 코드로 못 푼다. 대신 사이트 레시피가 가드를 직접 지정하면 모델 판단 없이 붙는다(제안 1).
- 이번 벤치 작업문 "눌렀으면 done 하세요" 가 관찰을 유도했을 가능성은 있으나, 사용자 지시가 흔히 그런 형태라 벤치를 바꾸지 않았다.

## 5. 다음 업그레이드 제안 3개

1. **레시피 내장 가드** — 네이버 발행 레시피처럼 인스타·유튜브 게시 흐름을 만들 때 완료 문구·URL 변경 가드를 레시피가 지정(모델 채택률 의존 제거). 실사이트 파일럿과 함께.
2. **자동 가드(시스템 측)** — 모델 응답이 `click` 하나뿐이고 작업문이 단일 동작("눌러라·클릭해라")이면 시스템이 `expect{changed}`+`done` 을 붙일지 검토. 단 "완료를 모델이 아닌 시스템이 선언" 하는 것이라 정직성 규칙(발행·위험 제외, 변화 요약 필수)과 옵트인 설정이 전제.
3. **벤치 이력 추세** — 프롬프트 한 줄에 호출 수가 오가므로 결과를 이력으로 쌓아 회귀 감시.
