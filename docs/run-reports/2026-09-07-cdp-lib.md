## 2. 내린 결정과 이유

| 결정 | 이유 |
|------|------|
| **접속 계층만 공유, 앱 spawn·프로필·시나리오는 각자 소유** | 하네스마다 기동 방식·프로필 시드가 다르다. 거기까지 합치면 이득은 작고 회귀 위험만 커진다 |
| **`CDPSession` 을 상위집합으로** | agent-safety 는 `events` 로 Electron `webContents.debugger` 를 흉내낸다(A11 파일창 가로채기). 다른 하네스에는 무해하므로 삭제하지 않고 흡수 |
| **`sleep`/`withTimeout`/`pollUntil` 은 각 하네스에 그대로 둠** | 이름 충돌을 피하려면 지역 정의를 지워야 하는데, 그 편익보다 변경 면적이 커진다. lib 은 자체 사본을 쓴다 |
| **perf 콜드 스타트 경로도 교체** | 콜드 스타트 수치는 앱 내부 latched 마일스톤(`perf.report()`)에서 오고 CDP 접속 시간이 아니다 — 코드 주석으로 확인. 측정치에 영향 없음 |
| **perf 판정을 private 기준으로 교정** | CLAUDE.md 가 명시적으로 WorkingSet 은 "판정에 쓰지 말 것"이라 했는데 하네스가 그걸로 실패시키고 있었다. 늘 빨간 게이트는 무시당한다 |
| **예산 숫자 자체는 손대지 않음** | 254MB(예산 250MB)는 측정 결과다. 통과시키려고 예산을 고치는 것은 검증이 아니라 은폐 |

### ⚠ 자동 변환이 조용히 코드를 삼킨 사고 (검출·복구함)
1차 변환기가 블록 끝을 "열 0의 `}`"로 판정했다. **한 줄 함수**
(`async function getTargetList(port) { … }`)를 만나면 그 줄에서 끝나지 않아 **다음 블록까지 삼켰다.**
압축형 3개 파일(probe-fingerprint · verify-agent-safety · verify-fixes)에서
`isShellTarget` · `shellWindowId` · `startProbeServer` · `startPageServer` 등이 사라졌는데
**`node --check` 는 전부 통과했다** — 선언 소실은 문법 오류가 아니기 때문이다.

**검출 방법**: 이식 전/후의 최상위 선언 집합을 비교해 "사라졌는데 여전히 사용되는 이름"을 찾는 감사.
3건 전부 걸렸고, 백업 복원 후 **중괄호 깊이 추적** 방식으로 재이식해 파손 0 을 확인했다.
→ **교훈: 자동 리팩터링에 문법 검사만으로는 부족하다. 심볼 수준 감사가 필요하다.**

### perf 게이트가 항상 실패하던 버그
`perf-measure` 는 예산 표의 판정 문자열을 `includes('FAIL')` 로 봤다. 그런데 그 문자열에는
참고용 WorkingSet 판정(`private=PASS / WS=FAIL`)이 함께 들어 있어서, **모든 예산을 통과해도
언제나 exit 1** 이었다. CLAUDE.md 는 Electron 의 `workingSetSize` 가 공유 페이지를 5~7배
중복 집계하므로 "판정에 쓰지 말 것"이라 명시한다. → private 판정만 실패로 세도록 교정하고,
초과 항목명을 출력하게 했다.

교정 후 실측(같은 세션 2회):
| 항목 | 1회차 | 2회차 | 예산 | 판정 |
|------|-------|-------|------|------|
| 콜드 스타트 | 401ms | — | 2000ms | PASS |
| 빈 창 RSS(private) | **242MB** | **254MB** | 250MB | 경계에서 변동 |
| 탭당 증가(private) | 15.2MB | — | 80MB | PASS |
| 휴식 CPU | 0.026% | — | 0.5% | PASS |

## 4. 못 한 것과 이유

| 항목 | 사유 |
|------|------|
| **perf 빈 창 RSS 경계 문제** | 같은 세션에서 242MB ↔ 254MB 로 예산선(250MB) 위아래를 오간다. V4가 문서화한 웜(≈226MB)/콜드(≈285MB) 구간의 경계다. **예산을 고쳐 통과시키지 않았다** — 하네스가 웜 경로를 확실히 재게 하거나 콜드 완화 조항을 판정에 반영하는 것이 옳고, 그건 별도 라운드의 판단이다 |
| `verify-fixes` · `perf-breakdown` 실행 | 이식·구조 검증만 함. 러너 등록부에 없는 일회성 진단 도구라 우선순위를 낮췄다. **돌리지 않은 것을 통과로 쓰지 않는다** |
| `git push` / 원격 | **가드레일** — 로컬 커밋만 |

### 관찰 (수정 안 함)
1. **agent-safety A14 간헐 실패** — 10회 클릭 중 9회 도달(오클릭 0), 재실행 시 10/10.
   이식과 무관한 기존 flake다(접속 계층이 아니라 입력 전달 경로). 판정이 10/10 만점을 요구해 흔들린다.
2. 어제 `--full` 을 무너뜨린 환경 지연은 **오늘 재현되지 않았다**(스모크 13초, 전 하네스 정상).
   누적된 미종료 인스턴스가 주된 요인이었을 가능성이 크다.

## 5. 다음 업그레이드 제안 3개

1. **perf 웜 경로 확정 + 콜드 완화 조항 코드화** — 지금은 같은 코드가 242/254MB 를 오가며
   게이트가 동전 던지기다. CLAUDE.md 의 "웜 250MB / 콜드는 adblock 고정비만큼 완화"를
   하네스 판정에 반영하고(측정 모드를 명시적으로 warm/cold 로 나눔), 결과에 어느 경로였는지 기록. 규모 S~M.

2. **A14 판정 기준 재검토** — "10/10 만점"은 실제 입력 전달의 성격상 간헐 실패를 낳는다.
   3회 중 최고값 채택 또는 9/10 허용 + 오클릭 0 필수처럼, **막고자 하는 회귀(오클릭)**를
   정확히 겨냥하도록 판정을 바꾸는 편이 게이트의 신뢰를 높인다. 규모 S.

3. **`verify-all --full` 완주 + 기준선 기록** — 이제 모든 하네스가 개별로는 통과함을 확인했으니,
   한 번에 이어 돌려 각 단계 소요·결과를 `verify-all-results.json` 기준선으로 남긴다.
   현재 회수 시계 값은 여전히 추정치다. 규모 S.
