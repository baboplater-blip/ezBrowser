## 2. 내린 결정과 이유

| 결정 | 이유 |
|------|------|
| **하네스를 고치지 않고 감싸기** | 11개 하네스를 손대면 회귀 위험이 그만큼 커진다. 종료 코드 규약(0/1/2)이 이미 일관돼 있어 감싸기만으로 충분했다 |
| **판정을 2단으로(종료코드 + 결과 JSON)** | 종료 코드만 보면 하네스가 실패를 삼킬 때 못 잡고, JSON만 보면 낡은 파일에 속는다 |
| **결과 JSON은 "단계 시작 이후에 쓰인 것"만 인정** | 실제로 거짓 통과를 봤다 — 부팅 단계에서 죽은 하네스가 이전 실행의 `PASS 14`를 그대로 보고했다 |
| **잔재 앱 정리는 "이 실행 이후에 뜬 것"만** | 사용자가 열어둔 창을 죽이지 않기 위한 안전 조건. 시각 조건이 그 보증이다 |
| **exe 잠금은 죽이지 않고 BLOCKED 보고** | 잠근 주체가 사용자의 창일 수 있다. 판단은 사람이 한다 |
| **고의 실패 주입을 검증에 포함** | 게이트가 실패를 삼키지 않는지는 "성공 실행"으로 증명되지 않는다 |
| **3회 실패 후 `--full` 추격 중단** | 규범(동일 실패 3회 → "못 한 것"). 원인이 제품이 아니라 머신 상태임을 측정으로 확인한 뒤 중단 |

## 3. 검증 결과

### 게이트로서 작동하는가 (핵심 검증)
| 검증 | 방법 | 결과 |
|------|------|------|
| **실패를 종료 코드로 전파** | `app/main/__verify_all_probe.ts` 에 고의 타입 오류 주입 | ✅ `typecheck FAIL` + 실패 로그 꼬리 출력 + **exit 1** (주입 제거 후 정상 복귀) |
| **exe 잠금 사전 차단** | 앱을 띄운 채 `--only package` | ✅ `BLOCKED`, **PID 지목**, 사용자 창 미종료, exit 1 |
| **낡은 결과 파일 무시** | 부팅 실패한 하네스의 이전 결과 | ✅ mtime 조건으로 거짓 `PASS 14` 차단 |
| **잔재 앱 정리** | 앞 단계가 남긴 인스턴스 | ✅ `잔재 앱 5개 정리 (PID …)`, 안 죽는 것은 **⚠ 경고로 보고** |
| **회수 시계** | 스모크가 종료 단계에서 정지 | ✅ 10분에 TIMEOUT 처리 후 다음 단계 진행 |
| **`--quick` 실전** | 깨끗한 머신 상태 | ✅ **4/4 PASS**(typecheck·build·package·스모크 16/16), exit 0 |
| **`--full` 실전 완주** | 11단계 | ❌ **실패 — 4절 참조** |

### 그 과정에서 잡은 실제 결함 3건
1. **테스트 서버 종료 정지(모든 하네스 공통)** — `server.close()` 가 앱의 keep-alive 연결을 기다려
   영영 끝나지 않는다. 스모크가 **16/16 통과 후 종료 단계에서 8분 이상 정지**한 것이 실측 증거.
   앞선 성공들은 그 순간 소켓이 마침 없었던 운이었다.
2. **`taskkill /F` 가 죽음을 보장하지 않음** — "정리했다"고 보고한 PID가 그대로 살아 **디버그 포트를 쥐고** 있었다.
   두 번째 `taskkill` 에 죽었다. 확인·재시도 없는 정리는 정리가 아니다.
3. **4개 하네스의 기본 `--out` 이 죽은 절대경로** — 사람이 직접 돌리면 결과가 존재하지 않는
   옛 임시 디렉터리로 흩어진다.

### ⚠ 임무 A 보고의 원인 설명 정정 (중요)
임무 A에서 스모크 INFRA 실패를 **"실행 컨텍스트 미생성 시점의 명령 유실"** 로 적었다. **틀렸다.**
그때 "패치 후 3/3"은 마침 잔재 프로세스가 없었기 때문이고, 원인은 다음 둘이었다(측정으로 확정):

1. **좀비 인스턴스의 포트 선점** — 남은 앱이 디버그 포트를 쥐면 `/json/list` 가 **죽은 좀비의 타깃**을
   돌려준다. 새로 띄운 앱이 아니라 시체에게 말을 걸고 있었던 것. (로그 증거:
   `이전 실행이 남긴 프로세스 발견 (pid=35624, port=9223)` → 이후 18회 시도 전부 무응답)
2. **갓 패키징한 exe 의 첫 CDP 응답 지연** — 같은 머신에서 **20ms ↔ 16초**로 변동(백신 검사·콜드 캐시 추정).
   인내심 있는 단일 세션 측정으로 **16.07초** 실측. 짧은 타임아웃 + 재연결 반복은 늦게 오는 응답을
   **매번 버려서** 영원히 실패한다.

임무 A의 `connectShellSessionReady` 자체는 유효한 개선이었지만(재시도·재연결·pending 정리),
**대기 시간이 너무 짧아 오히려 이 지연을 못 견뎠다.** 이번에 8s→20s→30s / 총 90초로 확대하고
`evaluate` 기본 타임아웃도 15s→30s 로 올렸다.

## 4. 못 한 것과 이유

### `--full` 완주 실패 (가장 중요)
- **증상**: 오전에 같은 코드로 스모크가 16/16을 3회 연속 통과했으나, 오후~새벽에는 INFRA 단계에서 반복 실패.
- **원인(측정으로 확인)**: ① 위 정정 ②번의 CDP 응답 지연이 이 머신에서 심해졌고,
  ② 내가 반복 실행하며 **죽지 않는 인스턴스가 누적**되어 서로를 느리게 만드는 악순환이 생겼다.
- **앱은 정상이다** — 모든 실패 실행에서 `[adblock] initialized (standard, filters=4, all sessions)` 정상 출력,
  크래시 0, `npm run typecheck` 0 에러, `--quick` 4/4 통과 실적 존재. **제품 회귀가 아니다.**
- **재시도 방법**: 머신 재부팅(또는 `dist/win-unpacked` 를 백신 예외 등록) 후
  `npm run verify` → 통과하면 `npm run verify:full`. **패키징 직후 바로 돌리지 말 것.**
- 3회 연속 동일 실패로 규범에 따라 중단했다. 러너 자체의 결함이 아니라 실행 환경 문제이며,
  러너는 이 상황에서 **실패를 정확히 보고**했다(그게 러너의 일이다).

### 그 밖에
| 항목 | 사유 |
|------|------|
| `git push` / 원격 | **가드레일** — 로컬 커밋만 |

| z-order(Z1/Z2) 자동 판정 | 여전히 스크린샷 촬영까지만 (임무 A와 동일) |

## 5. 다음 업그레이드 제안 3개

1. **CDP 접속 견고화 5개 하네스 이식** — `connectShellSessionReady`·`ensureSessionReady`·포트 점유 확인·
   `waitForPortFree` 를 `dl-matrix`·`ext-matrix`·`session-restore`·`stress`·`perf-measure` 에 이식.
   이번에 스모크에서만 고쳤고, 나머지는 같은 코드에서 복제돼 **동일한 취약점을 그대로 갖고 있다**.
   공통 모듈(`build/lib/cdp.mjs`)로 추출하면 다음 하네스부터 자동으로 안전해진다. 규모 M.

2. **`--full` 완주 + 결과 기준선 확보** — 재부팅/백신 예외 후 한 번 완주시켜
   각 단계의 실제 소요·통과 여부를 `verify-all-results.json` 기준선으로 남긴다.
   이 기준선이 있어야 회수 시계 값을 근거 있게 조정할 수 있다(지금은 추정치). 규모 S.

3. **z-order 자동 판정** — Z1/Z2가 "촬영 성공"까지만 보는 한, 임무 A에서 고친 오버레이 회귀가
   재발해도 게이트는 초록으로 통과한다. OS 스크린샷의 지정 영역 픽셀을 기대 색과 비교하는
   최소 판정기를 붙이면 사람 눈 없이도 막을 수 있다. 규모 M.
