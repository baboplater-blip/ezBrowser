## 2. 내린 결정과 이유

| 결정 | 이유 |
|------|------|
| **후보별 A/B → 전부 끄기 → 이분 탐색** 으로 전략 전환 | 부팅 간 산포가 15~18MB라 10MB 미만 후보를 개별 분리할 수 없었다. 측정 횟수를 후보 수가 아니라 log 로 줄이는 쪽이 옳다 |
| **"전부 끄기"도 차이 없자 방법 자체를 바꿈** | 같은 방법으로 표본만 늘리면 시간만 든다. **부팅 간 노이즈가 문제라면 한 부팅 안에서 재면 된다** — 노이즈가 원천적으로 없다 |
| **판정 규칙(산포 대비)을 완화하지 않음** | 규칙을 느슨하게 하면 임무 4·5의 오판이 그대로 재현된다. 규칙은 두고 **측정을 개선**했다 |
| **AI 를 대조군으로 먼저 측정** | "차이 없음"이 나와야 정상인 항목으로 절차 자체를 검증했다(실제로 -1MB, 차이 없음 판정) |
| **임시 스위치 전량 제거** | 측정용 코드는 제품에 남기지 않는다. 되돌린 뒤 typecheck·스모크로 확인 |

## 3. 검증 결과

### ① 부팅 초기화 A/B — 전부 "차이 없음"
| A/B | 중앙값 차이 | 산포 | 판정 |
|-----|------------|------|------|
| 전체ON vs **AI-off**(대조군) | -1MB | 16MB | 차이 없음 ✅(예상대로) |
| 전체ON vs **6종 전부 OFF**<br>(DB·policy·misc·media·AI·client-hints) | **-6.5MB** | 18MB | **차이 없음** |

→ 부팅 초기화 6종을 **모두 꺼도** 정상상태 메모리는 유의하게 줄지 않는다.

### ② 한 부팅 안에서의 초기화별 rss 증분 (노이즈 없음)
```
start                    rss  86MB
db(sql.js)      +60.9MB  rss 146MB   ← 압도적
workspaces       -3.6MB  rss 143MB
userscript       +0.5MB
policy           +0.5MB
misc(pw/tokens/auto/mod) -7.1MB      ← GC 회수 시작
ipc             -12.1MB
actions         -15.9MB
downloads/media/translate/qrcode/ai  각 ≤ +0.9MB
                         rss 111MB (초기화 종료)
```
- **sql.js 가 순간 +61MB** 를 쓰고, 이후 GC 가 대부분 회수한다(146 → 111MB)
- 나머지 초기화는 **전부 1MB 이하** — ①의 "차이 없음"과 정확히 일치한다
- 즉 sql.js 는 **정상상태 비용은 작지만 피크 메모리 최대 항목**이다

### ③ adblock — 진짜 주범 (노이즈를 압도)
| 구성 | 표본 | 중앙값 | 산포 |
|------|------|--------|------|
| adblock-ON | 3 | **257MB** | 3MB |
| adblock-OFF | 3 | **147MB** | 19MB |

**중앙값 차이 = 110MB · 산포 19MB → 도구 판정 "차이 있음"**

- adblock 하나가 빈 창 메모리의 **약 44%**(110/257)
- V4(2026-07-11) 기록 ≈107MB 와 사실상 동일 → **adblock 은 커지지 않았다**
- adblock 을 끄면 **147MB** — 예산(250MB)에 100MB 여유

### 회귀 확인 (임시 코드 제거 후)
`npm run verify` **4/4 PASS**(typecheck·build·package·스모크 16/16), 앱 코드 최종 변경 **0**(`git status` 로 확인).

## 4. 못 한 것과 이유

### V4 대비 +24MB 의 출처는 **끝내 특정하지 못했습니다**
- 주요 후보는 **배제**했다: adblock(변화 없음 110 vs 107), 부팅 초기화 6종(전부 꺼도 차이 없음), sql.js(정상상태 기여 작음)
- 남은 가능성: 외피 렌더러 번들 증가(gzip 72→99KB), Chromium/Electron 내부 변동, 그리고 **개별로는 탐지 한계(15~18MB) 미만인 여러 작은 증가의 합**
- 이 머신의 **부팅 간 분해능이 ±15~18MB** 라, 24MB를 여러 조각으로 나눠 찾는 것은 원리적으로 불가능하다. **억지로 원인을 지목하지 않는다**

### 그 밖에
| 항목 | 사유 |
|------|------|
| 임시 스위치를 제품에 남기기 | 하지 않음 — 측정용 코드는 제품 코드가 아니다 |
| `git push` / 원격 | **가드레일** — 로컬 커밋만 |

## 5. 다음 업그레이드 제안 3개

1. **예산 표에 adblock 비용을 명시하고 재기준화** — 이제 숫자가 확정됐다:
   **빈 창 250MB 중 adblock 110MB**, adblock 없으면 147MB. CLAUDE.md 는 이미 콜드 완화 조항을
   두고 있지만, **웜에서도 adblock 이 110MB를 쓴다는 사실이 예산 표에 없다.**
   "빈 창 ≤250MB(adblock 포함) / ≤150MB(adblock 제외)" 처럼 **두 줄로 적으면**
   게이트가 동전 던지기를 멈추고, 회귀도 어느 쪽에서 났는지 즉시 보인다. 규모 S.

2. **sql.js 지연 로드 — 피크 메모리 61MB 회수** — 정상상태 기여는 작지만 **부팅 순간 +61MB**를
   쓴다. 북마크·이력을 실제로 조회할 때까지 미루면 **콜드 스타트 피크**가 크게 내려간다
   (저사양 머신에서 체감되는 지점). 임무 5의 AI 지연 로드와 달리 **이번엔 숫자가 확실하다**. 규모 M.

3. **A/B 도구에 "탐지 한계" 자동 보고** — 지금은 사람이 산포를 보고 "이 정도는 못 잡는다"를
   판단한다. 도구가 **"이 표본 수·산포에서는 X MB 미만을 탐지할 수 없음"** 을 먼저 출력하면,
   애초에 무의미한 측정을 시작하지 않는다. 오늘 나는 그걸 두 번 시도한 뒤에야 알았다. 규모 S.

## 부록 — 방법론 교훈

**부팅 간 A/B 로는 10MB 미만을 볼 수 없다. 한 부팅 안에서 재면 0.1MB 도 보인다.**
같은 질문에 두 방법이 있었고, 노이즈 구조가 완전히 달랐다. 앞으로 "무엇이 메모리를 쓰나"는
**먼저 한 프로세스 안에서** 재고, 정상상태 비교가 필요할 때만 A/B 로 넘어간다.
