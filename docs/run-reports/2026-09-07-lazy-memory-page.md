## 3. 검증 결과

### ① 기각의 근거 (측정·조사)
- `pages/newtab/index.html`: 로드 시 `history.topSites(12)` · `bookmarks.list()` · `history.recent(8)` 호출
- 부팅 첫 탭이 새 탭이므로 **DB 는 1초 안에 필요**하다 → 지연은 피크를 없애지 못한다
- `storage/db.ts`: `let SQL` 모듈 캐시 → 두 DB 가 sql.js 런타임을 공유(중복 없음)
- 저장소 API 는 전부 **동기**(`listBookmarks()`·`isBookmarked()`·`topSites()` …)라, 진짜 지연은 API 를 async 로 바꾸는 광범위 리팩터를 요구한다(17 호출·9파일)
- **결론**: 비용은 크고 이득은 없다 → 짓지 않음

### ② `browser://memory` — 사용자에게 보이던 거짓 판정 수정
| 전 | 후 |
|----|-----|
| `빈 창 RSS ≤ 250MB` 를 **workingSet 합(≈750MB)** 과 비교 → 항상 빨강 | 비교 제거. 예산 줄은 **하네스 실측값**(adblock 제외 145MB / 총계 249MB · 그중 adblock ≈104MB)을 기준선으로 표시 |
| 전체 메모리 1개 카드 | **메인 private bytes** + **전체 WorkingSet(참고·과대)** 2개 카드 |
| 지표 설명 없음 | 안내 문구 2개: "예산은 private working set 기준이라 이 페이지에서 정확히 잴 수 없다 — 정확한 판정은 `npm run verify:full`", "private bytes 는 커밋 기준이라 WMI private working set 과 다르다" |

**실기 확인**(CDP 로 `browser://memory` 를 열어 DOM 검사):
```
hasMainPriv: true · hasNoAdblockLine: true · hasHint: true · stillCompares: false · JS 오류 없음
표시 예: 282MB(메인 private bytes) | 754MB(전체 WorkingSet) | adblock 제외 목표 ≤155MB | ✓ 하네스 실측 145MB
```

### ③ A/B 탐지 한계 사전 보고
```
[perf-breakdown:AB] 예상 탐지 한계 ≈ 12.7MB (관측 산포 18MB 가정, 표본 2회)
[perf-breakdown:AB] 이보다 작은 기여도는 이 조건에서 "차이 없음"으로 나온다 — 더 작은 것을 보려면
[perf-breakdown:AB] 표본을 늘리거나, 한 부팅 안에서 재는 방식(초기화 전후 rss 증분)을 쓸 것.
```
"차이 없음" 판정에도 한계값을 다시 붙여, **원인 부재로 오해하지 않게** 했다.

## 4. 못 한 것과 이유

| 항목 | 사유 |
|------|------|
| **sql.js 피크 61MB 회수** | 위 ① — 지연으로는 불가능. 줄이려면 **sql.js 자체를 바꾸는**(더 작은 WASM 빌드, 또는 better-sqlite3 같은 네이티브로 회귀) 접근이 필요하고, 그건 저장소 계층 교체라 별도 대형 라운드다 |
| 메모리 페이지에서 **정확한 private working set** 표시 | Electron API 로는 프로세스별 private working set 을 얻을 수 없다(WMI 필요). 페이지에서 WMI 를 부르는 것은 사용자 브라우저에서 외부 프로세스를 스폰하는 일이라 하지 않았다 |
| `git push` / 원격 | **가드레일** — 로컬 커밋만 |
