# 세션 복원 내구성 라운드 — 크래시 뒤 사라지던 탭 (2026-09-20)

직전 라운드가 **고치지 않고 남긴 관찰**을 닫는다:

> "강제 종료 뒤 두 번째 탭이 세션 복원으로 살아나지 않는 경우를 하네스 작업자가 실측했다.
>  … 이번 범위가 아니라 손대지 않았다. 하네스는 재부팅 후 같은 URL 로 탭을 다시 열어 우회했다."
> — `.auto-dev/interruption-recovery-20260919-final.md` 5절

그 우회(하네스가 탭을 다시 열어 준 것)가 결함을 가리고 있었으므로, 이번에는 **먼저 재현**하고
원인을 특정한 뒤에만 고쳤다.

> ⚠ 실제 소스는 `app/main/features/session/index.ts` 다(`app/main/session` 이 아니다).
> 스킬 문서 `tab-restore-session` 의 원칙은 따르되, 스키마·경로는 **현재 소스가 정본**이다.

---

## 1. 무엇이 실제로 망가져 있었나

### C1 — 저장 기한이 **뒤로 밀렸다** (탭이 사라진 직접 원인)

`scheduleSave` 는 타이머가 **하나**였고, 모든 이벤트가 그 타이머를 **다시 깔았다**.

- 탭을 만들면 `tabEvents 'list'` → `scheduleSaveSoon()` → **1초 뒤 저장** 예약
- 그런데 그 페이지가 로딩되며 제목·파비콘·로딩 상태가 바뀌면 `'update'` → `scheduleSave(5000)` →
  **방금 예약한 1초 기한을 지우고 5초로 다시 깐다**

제목이 5초보다 자주 바뀌는 동안에는 이 일이 계속 반복된다. 즉 **새로 연 탭이 디스크에 한 번도
닿지 못한 채** 30초 강제 저장을 기다리게 된다. 그 구간에 강제 종료가 나면 그 탭은 복원되지 않는다.

**기전 수준 실측 (순수 로직, 가상 시계):** 탭 생성(기한 1초) 직후 제목 변동 80회를 흘리면

| | 저장 기한 |
|---|---|
| 고치기 전 | **9,000 ms** (8초 밀림) |
| 고친 뒤 | **1,000 ms** (그대로) |

### C2 — 스냅샷 항목 하나가 **그 창의 나머지 탭을 통째로** 날릴 수 있었다

복원 루프는 디스크에서 읽은 탭 항목을 그대로 믿고 `createTab({ url: t.url })` 을 불렀다.
`createTab` 은 `initialUrl.startsWith('browser:')` 를 하므로 `url` 이 문자열이 아니면 **TypeError** 가
나고, 그 예외가 `w.tabs.forEach` 를 빠져나가 **뒤따르는 탭 전부**가 만들어지지 않는다.

### C3 — 복원 직후에는 디스크에 복구 자료가 **하나도 없었다**

`maybeRestoreSession` 은 복원을 마치자마자 `current.json` 을 지웠다. 복원된 탭들은 아직 URL 을
커밋하지 않아 첫 라이브 저장은 그보다 뒤에 온다. 그 사이에 다시 크래시가 나면(같은 원인으로
연달아 죽는 것은 드문 일이 아니다) **그 세션은 완전히 사라진다.**

### C4 — 쓰기가 실패해도 옛 복구 자료를 지웠다

`writeSnapshot` 은 실패를 경고만 하고 삼켰고, `before-quit` 은 그 성패와 무관하게
`safeUnlink(currentPath())` 를 불렀다. 디스크가 가득 찼거나 경로가 막힌 그 순간,
**남은 복구 자료가 0개**가 된다.

### C5 — 아직 커밋되지 않은 탭은 스냅샷에서 **통째로 빠졌다**

`collectSession` 은 `wc.getURL()` 을 썼는데, 이 값은 첫 커밋 전까지 빈 문자열이다.
그 상태의 탭은 `if (!url) continue` 로 조용히 빠진다 — 즉 **막 연 탭**일수록 스냅샷에 없다.
C1 과 겹치면 "방금 연 탭이 사라진다"가 두 겹으로 일어난다.

## 2. 무엇을 고쳤나

| # | 고친 것 | 파일 |
|---|---|---|
| C1 | 저장 기한을 **둘로 분리**. 구조 변경(탭 추가·삭제·이동·핀·이동)의 기한은 **앞당겨질 수만 있고 뒤로 밀리지 않는다.** 제목·파비콘은 예전처럼 합쳐진다(매 이벤트 디스크 쓰기 아님). | `session/save-deadlines.ts`(신규) · `session/index.ts` |
| C2 | 디스크에서 읽은 스냅샷을 **항목 단위로 검증**. 못 쓰는 탭만 빠지고 나머지는 산다. 복원 루프의 탭·그룹·레이아웃 각각에 예외 격리. | `session/snapshot-schema.ts`(신규) · `session/index.ts` |
| C3 | 복원 성공 뒤 `current.json` 을 **지우지 않는다**. 라이브 저장이 곧 덮어쓰고, 정상 종료가 지운다. 사용자가 "새 탭으로 시작" 을 고른 경우에만 즉시 지운다(명시적 결정). | `session/index.ts` |
| C4 | `writeSnapshot` 이 **성공 여부를 반환**하고, `before-quit` 은 **새 자료를 확실히 쓴 뒤에만** 옛 자료를 지운다. 실패한 `.tmp` 는 치운다. | `session/index.ts` |
| C5 | 커밋 전 탭의 요청 URL(`pendingUrl`)을 들고 있다가 `getURL()` 이 비었을 때만 대신 쓴다. | `tabs/tab-service.ts` |

### 일부러 하지 않은 것

- **손상된 파일을 조용히 덮어쓰지 않는다.** 읽을 수 없는 스냅샷은 `<이름>.corrupt` 로 **옮겨 두고**
  로그를 남긴다. 이름을 고정해 부팅마다 쌓이지 않게 했다 —
  직전 라운드에 *정상* 파일을 매 부팅 격리해 쌓던 사고(D5)가 있었기 때문이다.
- **스키마 버전이 다른 파일은 "손상" 이 아니다.** 격리하지 않고 그냥 쓰지 않는다.
- **복원이 여는 스킴을 넓히지 않았다.** 저장할 때와 같은 규칙(`http(s):`·`browser:`)만 통과한다.
- **30초 강제 저장 주기는 줄이지 않았다.** 구조 변경 기한이 고쳐졌으므로 불필요한 IO 만 늘린다.

### 디스크 증거 (그대로 옮김)

**SD1 — 두 탭을 열고 1.5초 뒤 강제 종료**

```
고치기 전:  preKillCurrent  = {"exists": false, ...}      ← 세션 파일이 아예 없다
            postKillCurrent = {"exists": false, ...}
            restoredUrls    = ["browser://newtab/"]        ← 두 탭 다 사라졌다

고친 뒤:    preKillCurrent  = {"exists": true, "tabUrls": ["…/p?n=1", "…/p?n=2"]}
            restoredUrls    = ["…/p?n=1", "…/p?n=2"]
```

> **보고서의 표현을 정정한다.** 직전 라운드는 "두 번째 탭이 살아나지 않는다" 고 적었지만,
> 실측은 **두 탭 다** 사라진다. 첫 탭도 저장된 적이 없었다.

**SD2 — 제목이 300ms 마다 바뀌는 페이지**

```
고치기 전:  measuredLatencyMs = null   (12초 동안 끝내 저장 안 됨)
고친 뒤:    measuredLatencyMs = 845 ms (한도 3000ms)
```

**SD4 — `last-stable.json.tmp` 자리에 디렉터리를 놓아 쓰기를 실패시킨 뒤 정상 종료**

```
고치기 전:  survivingSource = "(없음 — 유실)"     ← current 도 last-stable 도 없다
고친 뒤:    survivingSource = "current.json"  (탭 2개 그대로) → 재기동 시 복원됨
```

**SD5 — 가운데 항목만 `{"url": 42}` 인 세 탭짜리 파일**

```
고치기 전:  finalUrls = ["browser://newtab/"]              ← 멀쩡한 두 탭까지 사라졌다
고친 뒤:    finalUrls = ["…/p?n=1", "…/p?n=3"]  · 원본 파일은 보존됨
```

### 음성 대조 (검사가 실제로 결함을 잡는지)

컴파일 산출물에 **옛 동작을 도로 넣어** 확인했다(그 뒤 재빌드로 복구, 산출물에서 확인):

| 되돌린 것 | 빨개진 검사 |
|---|---|
| 구조 기한도 매번 다시 깔기(옛 단일 타이머) | SS1 (기한 1000 → **9000**), SS3 |
| 탭 항목 검증 제거 | SS5 · SS8 · SS9 |

그리고 SD8 은 **대조군이 함께 들어 있다** — 같은 파일에서 일반 텍스트 칸(`SD8PLAINNICK…`)은
**찾히고** 비밀번호(`SD8SECRETPW…`)는 **안 찾힌다**. 검사가 폼 상태를 실제로 들여다본다는 증거다.

### 새로 덧붙인 검사 (요청된 제약의 확인)

- **SD8 — 비밀번호가 디스크에 적히지 않는다.** `sessions/current.json` 의 **바이트를 직접** 뒤진다
  (원문·base64·pageState 디코드 결과까지). 결과: `secretFoundOnDisk: false`,
  `plainTextFoundOnDisk: true`.
- **SD9 — 시크릿 창 탭은 디스크에도 복원에도 없다.** 이번 변경이 스냅샷을 **더 자주·더 일찍**
  쓰게 만들었으므로 시크릿 제외가 뚫리지 않았는지 확인해야 했다. 시크릿 탭이 실제로
  열렸는지(`incogTabOpened`)까지 같이 본다 — "안 열려서 통과" 를 배제하기 위해.

### 기존 검사 하나를 **고쳐** 썼다 (숨기지 않고 적는다)

`session-restore-cdp` 의 '스크롤 위치 복원'·'폼 입력값 복원' 이 수정 뒤 **FAIL** 로 나왔다.
원인을 파고든 결과 **복원 경로는 멀쩡했다** — 같은 빌드에서 종료 시점만 늦추면 18/18 로 통과한다.

- 스크롤·타자는 메인 프로세스에 **이벤트를 내지 않는다.** Chromium 이 그 값을
  내비게이션 항목(pageState)에 반영하는 데도 몇 초가 걸린다.
- 예전에는 저장이 **활동 5초 뒤 딱 한 번** 일어났고, 하네스는 "그 한 번" 을 기다린 뒤
  3초를 더 자고 종료했다 — 우연히 조건이 맞았다.
- 이제는 탭 목록을 지키려고 **1초 만에도** 저장이 뜬다. 하네스는 그 이른 저장을 보고
  3초 뒤 종료했고, 그 스냅샷의 pageState 는 아직 스크롤 전이었다.

그래서 **제품이 아니라 하네스의 대기 조건**을 고쳤다. 그리고 **느슨하게 하지 않고 조건을 늘렸다** —
예전 조건(탭 목록에 T7 과 scroll 이 있는가)은 스냅샷이 **언제** 떠졌는지를 전혀 제약하지 못한다.
이제 `savedAt` 하한을 걸어 **상호작용이 가라앉은 뒤에 떠진 스냅샷**을 기다린다.

같은 이유로 제품에도 하나를 덧붙였다: **구조 변경으로 일찍 뜬 저장은 "잠정" 으로 보고,
활동이 잦아든 뒤 한 번 더 뜬다**(활동 묶음당 최대 두 번 — 매 이벤트 IO 아님).
무한 저장 루프가 생기지 않는지는 SS14 가 못 박는다.

또 하나 고쳤다: '복원 후 current.json 정리됨' 판정은 **정상 종료가 끝난 뒤에** 측정되고 있었다.
그 시점엔 무엇을 확인하든 항상 "없음" 이 나온다 — 즉 아무것도 검증하지 않는 검사였다.
이제 **복원 직후(종료 전)** 에 재고, "파일이 있다" 가 아니라 **복원한 탭 URL 을 실제로 담고 있는지**를 본다.

## 6. 알려진 한계 (정직하게)

- **스크롤 위치·입력 중인 글자는 탭 목록만큼 자주 저장되지 않는다.** 마지막 상호작용 약 5초 뒤와
  30초 주기 저장에서 잡힌다. 그 사이에 강제 종료되면 **탭은 전부 돌아오지만 스크롤은 조금 전 것**이다.
  스크롤·타자가 메인 프로세스에 이벤트를 내지 않고 Chromium 의 pageState 반영도 지연되기 때문이다.
  **이 라운드 이전에는 같은 구간에서 탭 자체가 통째로 사라졌다** — 나빠진 것이 아니라 덜 나빠진 것이다.
- **이 설치파일의 설치→부팅→제거는 시험하지 않았다.** 이 PC 에 사용자 실설치본이 등록돼 있어
  무인 설치·제거가 그것을 덮어쓴다. **우회하지 않았다.** 설치 흐름의 정본 실증은 `rc.2` 까지다.
- **코드 서명 없음** — 사용자 제공 `.pfx` 가 필요하다.
- **검증은 전부 로컬 픽스처**다. 실제 사이트에서 돌리지 않았다.
- **동시에 여러 창**을 띄운 상태의 크래시는 시나리오에 없다(단일 창 기준).
- 30초 주기 저장은 줄이지 않았다 — 구조 변경 기한이 고쳐졌으므로 불필요한 IO 만 늘린다.
