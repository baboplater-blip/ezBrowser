## 코드를 고치기 전에 실패부터 재현했다

신규 하네스 `build/verify-recovery-cdp.mjs` 를 먼저 만들고, **수정 전 빌드 스냅샷**
(`.auto-dev/snapshots/recovery-flow-20260919/dist-before`)에 대고 돌렸다.
같은 하네스가 `--main` 으로 수정 전/후를 모두 잴 수 있다.

실제 별도 Electron 프로세스를 띄워 상태를 만든 뒤 **`taskkill /T /F` 로 강제 종료**하고 같은
`--user-data-dir` 로 재기동한다 — 정상 종료가 아니어야 "메모리 유실"이 증명된다.
종료는 **하네스가 spawn 한 PID 트리만** 대상으로 한다(이름 기반 종료 금지 — 사용자 앱 보호).

|---|---|---|

| **R3-POS** 정상 완료(양성 대조) | — | **PASS** — 정확히 **1건** 게시 + `stage=done` + 영수증 |

큰 순 정렬 때문에 미끼가 반드시 먼저 잡힌다.

## 고친 것

### A. 생성 기준선을 디스크로 (`capture.ts`)

- `userData/ai-image-baselines.json` — 기존 공용 `json-store`(원자적 tmp+rename·디바운스·손상 격리) 사용.
- **키 = `taskId` + 페이지 `origin`**. `tabId` 는 재시작하면 재발급되어 아무것도 매칭하지 못하므로
  기록만 하고 매칭에 쓰지 않는다. 옛 DOM ref·frameId 도 재사용하지 않는다.
- **민감 데이터 미저장**: 이미지 주소는 서명 URL·토큰을 포함할 수 있어 원본 src 대신
  `sha256(src)` 앞 32자만 남긴다. 메모리 표현도 같은 해시 — 경로를 하나로 유지한다.
- **상한·검증·버전**: `v:1`, 레코드 200개(오래된 것부터 정리), 레코드당 해시 500개,
  `/^[0-9a-f]{32}$/` 만 허용. 모양이 어긋난 레코드는 로드 시 버린다.
- **자동 채택 금지**: 같은 `taskId` **이고** 같은 origin 일 때만 쓴다. 다르면 "기준선 없음"이되
  **이유를 구분**해(`originMismatch`) 돌려준다 — 모델·사용자에게 정확히 설명할 수 있게.
- **덮어쓰기 방지(soft 모드)** — 이 라운드의 핵심: 재시작 후 그 페이지로 돌아오면 화면엔 **이미
  생성물이 그려져 있다**. 거기서 기준선을 다시 잡으면 생성물이 "원래 있던 것"으로 분류돼 영영
  못 찾는다. 그래서 `agent.ts` 의 **자동** 기준선(navigate 뒤·새 탭)은 `soft:true` 로 기존 기준선을
  덮지 않고, 모델이 **명시적으로** `mark_baseline` 을 부른 경우에만 덮어쓴다.
- **생성 버튼 재클릭 금지**: 기준선이 복원되면 `capture_image` 가 모델에게
  "이전에 잡아 둔 기준선을 복원했습니다(앱이 재시작됨). **생성 버튼을 다시 누르지 마세요** —
  이미 만들어진 결과가 있는지 먼저 확인합니다" 를 먼저 전달한다.

### B. 캡션 복구 (`social-workflow.ts`)

- `captionPending` 을 **디스크에 남긴다**. 재기동 시 `review` + `captionPending` + 캡션 없음이면
  `recovery = { kind:'caption-interrupted', … }` 로 정리한다. **부팅만으로 모델을 다시 부르지 않는다**
  (task-runtime 의 "재시작이 실행을 재개하지 않는다" 원칙과 동일).
- `retryCaption(id)` — **같은 보관 이미지 그대로**(`artifactId` 불변) 캡션만 다시 만든다.
- `setCaption(id, caption)` — 사용자가 직접 쓴 캡션을 저장하고 `captionUserEdited` 를 세운다.
  **늦게 도착한 모델 응답은 그것을 덮어쓰지 않는다**(`draftCaptionInto` 가 반영 직전에 확인).
- 취소·철회 뒤 늦게 온 응답은 `stage !== 'review'` 에서 걸려 **자동 게시 0건**.
- 원본 프롬프트를 캡션으로 대신 올리는 경로는 이전 라운드에서 이미 제거됐고, 이번에 건드리지 않았다.
- 선승인(`grant`)의 `used`·`consumed`·`expiresAt` 은 이미 영속이며, 재시작이 **새 승인이나 한도
  초기화가 되지 않는다** — `consumed` 가 같은 워크플로의 재자동게시를 막는다.

### C. 게시 불확실 복구 (`social-workflow.ts` + `task-runtime.ts`)

- 게시 작업이 `interrupted`/`needs-verify` 로 되살아나면 `publishUncertain` + `recovery` 를 세우고,
  `setResumeBlock(pubTaskId, …)` 으로 **그 작업의 이어가기를 코드로 막는다**
  (`resumeTask` 와 `startTask` 양쪽에 관문 — 한쪽만 막으면 우회된다).
- `resolvePublishUncertainty(id, choice)` 세 갈래:
  - `'verify'` — **읽기 전용** 확인 작업을 만든다(읽기 전용이 입력·업로드·run_js 를 이미 막는다).
    지시문이 결론을 **고정 표지**(`게시됨:` / `게시안됨:`)로 쓰게 하고, `parseVerifyMarker` 가
    맨 앞 앵커로만 판정한다. **표지가 없으면 증거로 인정하지 않고** 불확실을 유지한다 —
    모델의 자유 문장을 증거로 삼지 않는다.
  - `'published'` — 사용자가 직접 확인: 완료로 반영(`사용자 확인: 이미 게시됨`).
  - `'not-published'` — 이어가기 차단 해제.
  - **증거가 없으면 절대 다시 전송하지 않는다.**

## 게시 작업 유실 — 원인 확정과 수정 (run-20260919T064802Z-9a8e0a · 2026-09-19)

### 어떻게 갈랐나 (추정하지 않았다)

`build/verify-recovery-cdp.mjs` 의 R3 에 **진단 3점**을 넣어, 서로 다른 세 가지 가설을
따로 잴 수 있게 했다 — ① 킬 **직전** raw `ai-tasks.json` 에 있었나(=boot1 이 썼나)
② 킬 직후 raw 에 있나 ③ 제품이 load 한 뒤에도 있나(=`reviveTask` 가 버렸나).
`ai-tasks.json` 을 **제품 코드를 거치지 않고 직접** 읽는다(`rawTaskIds`).

| 관측 (수정 전 · `verify-out/recovery-diag`) | 값 |
|---|---|
| 킬 **직전** raw 에 게시작업 존재 | **false** |
| 킬 직후 / 재부팅 후 raw | false / false |
| raw 작업 수 | **1 → 1** (생성작업만. 게시작업은 한 줄도 안 쓰였다) |
| 워크플로 파일의 `taskIds.publish` | **보존됨(true)** — 두 저장소가 갈렸다 |
| 게시작업 생성 → 강제종료 | **1157ms** |

→ **"썼는데 load 에서 버려졌다" 가 아니라 "한 번도 쓰이지 않았다".**
직전 라운드에 남긴 "400ms·2s 를 감안하면 설명이 덜 된다" 는 **틀린 추론**이었다.
`json-store` 의 강제저장 상한 2000ms 는 *보장*이 아니라 **최악 지연의 상한**이다 — 변경이
쉼 없이 들어오면(에이전트는 매 단계 `markDirty` 한다) 첫 변경 이후 최대 2초까지 저장이 밀린다.
게시(비가역 외부 쓰기)는 그 창(1.16초) **안에서** 끝나 버렸다. 워크플로 저장소는 드물게만
건드려 400ms 타이머가 방해 없이 발화했기에 `taskIds.publish` 만 살아남았다.
같은 R3-NEG(전송 전 중단)에서는 앱이 더 오래 살아 있어 게시작업이 **정상적으로 남았다** —
같은 코드에서 결과가 갈린 것이 타이밍이라는 방증이다.

### 확증 (원인을 맞혔는지 되돌려 확인)

경계 하나를 넣자 같은 시나리오·같은 창(1150~1171ms)에서 **킬직전 false → true** 로 뒤집혔다.
다른 변수는 바꾸지 않았다. 이것이 원인 확정의 근거다.

### 고친 것 — 제품 결함 3건 (안전망 덧대기가 아니다)

1. **내구성 경계** (`social-workflow.ts` `runPublishStage`) — 게시 작업을 시작하기 **직전**,
   `flushTasks()` + 워크플로 `store.flush()` 로 "무엇을 하려 했는가(작업)" 와 "어느 워크플로의
   게시인가(binding)" 를 **둘 다** 디스크에 확정한다. 비용은 이 한 지점의 동기 쓰기 2회뿐이며
   **매 단계 동기 IO 가 아니다**(읽기·생성 단계는 그대로 디바운스).
2. **`queued` 로 되살아난 게시 작업이 아무 표시 없이 재시작 가능했다** (같은 파일 `reconcilePublish`)
   — ①을 고치자 드러난 **더 심각한 결함**이다. 작업을 디스크에 확정한 직후 `running` 으로 바뀌기
   전에 죽으면 `queued` 로 복원되는데, task-runtime 은 `queued` 를 `interrupted` 로 바꾸지 않고
   `reconcilePublish` 의 상태 분기 어디에도 걸리지 않았다 → **불확실 표시 없이 그냥 이어갈 수 있는
   상태**(= 같은 글 두 번). 실측에서 `ptaskStart` 가 3회 모두 성공했다.
   → 부팅 시점 스냅샷 `publishedBeforeThisBoot`(영속 아님)으로 "이번 부팅 **이전부터** 게시
   단계였는가" 를 가려, 그 경우의 `queued` 는 불확실로 남기고 이어가기를 막는다. 이번 세션에서
   막 만든 정상 `queued` 는 제외된다.
3. **거절을 성공으로 보고했다** (`task-runtime.ts` + `ipc/ai.ts`) — `startTask`/`resumeTask` 가
   `void` 라 차단이 제대로 걸려도 IPC 는 무조건 `{ok:true}` 를 돌려줬다. 사용자는 "이어가기" 를
   눌러도 **아무 일이 일어나지 않는 이유를 알 수 없었고**, 검사도 차단을 확인할 수 없었다.
