# 중단 복구 라운드 — 네트워크·제공자 오류와 사람 인계 (2026-09-19)

이번 범위: **자동화가 중간에 끊겼을 때** 같은 일을 두 번 하지 않고, 왜 멈췄는지 사람이 알 수 있게.
추측으로 리팩터링하지 않고 **먼저 재현한 결함만** 고쳤다.

---

## 1. 무엇이 실제로 망가져 있었나 (재현 후 확정)

### D1 — 댓글·좋아요 장부가 **클릭이 나가는 순간 디스크에 없었다** (가장 심각)

`blog-engage.ts` 의 중복 방지 장부(어느 글에 이미 댓글/좋아요를 했는가)와 행동 한도 카운터는
**디바운스 저장(300ms)만** 걸려 있었다. 에이전트 루프는 클릭 **직전에** 장부를 적지만
(`recordEngagement` → `markDirty()`), 그 기록은 **클릭이 실제로 나가는 시점에 아직 메모리에만** 있었다.

그 창 안에서 앱이 죽으면(크래시·강제 종료·정전) 재시작한 제품은 그 글을 "아직 안 건드렸다" 고 보고
**같은 글에 댓글을 또 단다**. 좋아요는 더 나쁘다 — 다시 누르면 **취소**된다.

게다가 `flushEngageLedger()` 는 export 만 돼 있고 **코드베이스 어디에서도 호출되지 않았다**
(`before-quit` 훅조차 없었다). 즉 **정상 종료로도** 마지막 300ms 의 기록이 사라졌다.

**재현 (수정 전, 순수 Node · 앱 없이 결정적):**

```
recordEngagement(...) + engageQuotaRecord(...) 직후
  메모리 alreadyDid = true
  디스크 장부(ai-engage-ledger.json)  = 없음     ← 클릭은 지금 나간다
  디스크 한도(ai-engage-quota.json)   = 없음
600ms 뒤
  디스크 장부 = 있음
```

이 라운드의 문서에는 **"같은 글에 두 번 달지 않습니다 — 재시작한 뒤에도 그 기록을 보고 건너뜁니다"**
라고 적혀 있었다(`docs/QUICKSTART.md`). 그 문장은 **중단이 없을 때만** 참이었다.

### D2 — 일반 에이전트 작업의 발행 원장에도 같은 창이 있었다

`task-runtime.ts` 의 `recordExternalWrite` 도 `markDirty`(400ms) 뿐이었다.
`social-workflow.ts` 의 게시 경로에는 `persistPublishBoundary()` 라는 내구성 경계가 있었지만,
**사용자가 직접 낸 일반 에이전트 작업의 발행 클릭에는 아무 경계도 없었다.**
발행 클릭 직후 강제 종료되면 원장이 사라져, 재시작 후 이어가기가 같은 글을 다시 올릴 수 있었다.

### D3 — 재시작이 **대기 사유를 지웠다**

`initTaskRuntime` 은 재시작 시 `waiting-user` 를 `interrupted` 로 정리하면서
`waitReason` 을 `"재시작으로 중단됐습니다 — 이어서 진행할 수 있습니다."` 로 **덮어썼다**.
무엇을 기다렸는지(`waitKind`)는 **휘발 상태에만** 있어 함께 사라졌다.

결과: **"🔐 로그인이 필요합니다"** 로 멈춘 작업도, **"결제하기 — 확인이 필요합니다"** 로 멈춘 작업도
재시작 뒤에는 똑같이 무해해 보이는 한 줄과 평범한 `▶ 이어가기` 버튼으로만 보였다.
사용자는 왜 멈췄는지 모르는 채로 이어가기를 누르게 된다.

### D5 — **정상적인 한도 파일이 매 부팅마다 "손상"으로 격리됐다** (검증 중 발견)

이건 찾으려던 것이 아니라 D1 검증 하네스가 **ED3 를 FAIL 로 떨구면서** 드러났다.

`json-store.ts` 의 `loadJsonObject` 는 최상위 `primaryKey` 가 **배열**일 것을 무조건 요구했다.
그런데 인게이지 한도 저장소(`ai-engage-quota.json`)는 `records` 를 **객체 맵**으로 쓴다
(`{ guardId: {comment, like, lastAt} }`). 그래서 **완전히 정상인 파일이 매번 손상으로 판정돼**
`.corrupt-*.bak` 으로 격리되고 카운터가 0 에서 다시 시작했다.

- 크래시가 아니라 **정상 종료 후 재시작**에서도 그랬다.
- `이 작업에서 댓글 N건까지` 같은 상한이 **재시작을 한 번도 넘기지 못했다** — 다시 켜면 한도가 부활한다.
- 덤으로 userData 에 손상본 파일이 부팅마다 쌓였다.
- 실패 경로가 "빈 상태로 시작" 이라 **아무도 죽지 않는다.** 로그 한 줄만 남고 기능이 조용히 무력화됐다.

**독립 재확인 (하네스와 무관하게, 제품 코드에 정상 파일을 직접 먹여):**

```
{"version":1,"records":{"g1":{"comment":2,"like":0,"lastAt":123}}}
  → loadJsonObject = null ("'records' 목록이 없음")
  → ai-engage-quota.json.corrupt-….bak 생성, 원본 소멸
```

### D6 — **발행 버튼 이름이 한 단어면 발행으로 분류되지 않았다** (검증 중 발견)

IR3 이 실패한 원인을 가르다가 드러났다. `agent-gate.ts` 의 `PUBLISH_RE` 에는
`공유$`·`share$`·`upload$` 처럼 **끝을 고정한** 갈래가 있다. 의도는 "버튼 이름이 **바로 그 단어**일 때만"
(`공유 정책` 같은 것에 걸리지 않게)이다.

그런데 제품이 실제로 만드는 라벨은 `describeAction()` 이 찍는 **`클릭 "공유"`** 모양이다 —
**뒤에 닫는 따옴표가 붙는다.** 그래서 그 갈래들은 **어떤 라벨과도 매치될 수 없었다.**

결과로 이름이 한 단어인 발행 버튼(`공유` · `Share` · `Post`)은:

1. **외부 쓰기 원장에 적히지 않았다** → 중복 게시 보호가 아예 걸리지 않았다.
2. **임시저장·발행 금지 모드의 하드블록을 그냥 지나갔다** → 초안만 만들어야 하는 작업이 **실제로 게시**될 수 있었다.
3. `publishClicks` 에 세지 않아 "이미 발행됨" 중복 가드와 정직한 done 경고도 발동하지 않았다.

**음성 대조로 검출력 확인** — 옛 판정에 같은 데이터를 먹이면:

```
미탐(발행인데 못 잡음) 5건: 클릭 "공유" · 클릭 "Share" · 화면 클릭 "공유" · 클릭 "Post" · 클릭 " 공유 "
오탐 0건
```

수정은 **넓히지 않는 방향**으로 했다. 라벨 전체로 한 번 보고, **클릭 라벨일 때만** 따옴표 안 이름을
좁은 목록(`공유|공유하기|발행|발행하기|share|publish|post`)과 대조한다.
`업로드`/`Upload` 는 **일부러 뺐다** — 유튜브 스튜디오처럼 그 버튼이 파일 선택 창을 여는 사이트가 많아,
발행성으로 보면 **초안 모드가 파일 첨부조차 못 하게** 된다. (검증이 내 첫 기대를 바로잡은 자리다.)
`입력 "공유" → …` 처럼 사용자가 **친 값**이 따옴표에 담기는 라벨도 타지 않는다.

### D7 — 제품 자신의 연결 실패 문구를 재시도 분류기가 못 알아봤다 (검증 중 발견)

IR1 의 `관측된 재시도종류=unknown` 이 단서였다. 오류 문구는
`AI 호출 중 오류: 로컬 Ollama 서버에 연결할 수 없습니다…` — 분명한 **연결 실패**인데 `network` 로 안 잡혔다.

`classifyRetry` 의 network 갈래는 한국어로 `연결하지 못` **하나만** 보고 있었는데,
제공자 계층(`providers.ts`)이 실제로 내보내는 것은 `연결할 수 없` 과 `연결 실패` 다.

차이는 사다리 길이다:

| 분류 | 재시도 |
|---|---|
| `unknown` (잘못 떨어진 곳) | **10초 1회** |
| `network` (맞는 곳) | 2초 · 8초 · 30초 **3회** |

즉 자리를 비운 사이 도는 긴 작업이 **일시적 연결 블립 한 번에 10초 만에 포기**하고 있었다.
그 파일의 주석이 바로 이 실패를 경고하고 있었다 — *"여기서 추측한 문구로 맞추면 분기가 전부
unknown 으로 떨어져 정책이 죽는다."* 실제로 죽어 있었다.

수정 후 격리 대조 **10건 전부 기대대로**(양성 6 · 부정 4 — `claude CLI 를 찾을 수 없습니다` 는
어휘가 달라 `unknown` 으로 유지된다).

### D4 — 미확인 발행이 있는데도 "재시도 중" 으로 표시됐다

구간이 오류로 끝나면 `runLoop` 이 원인을 분류해 바로 `scheduleRetry` 를 걸었다.
발행을 이미 눌렀는데 결과를 못 본 상태(= 서버에는 반영됐을 수 있고 응답만 유실)에서도 그랬다.
구간 시작의 원장 관문이 결국 잡기는 했지만, 그전까지 상태가 **진행 중인 것처럼** 보였고
백오프도 헛되이 태웠다. 불확실을 **더 일찍** 사람에게 넘겨야 한다.

### 물러서지 않은 지점

- **재시도를 통째로 끄지 않았다.** 읽기 전용·미커밋 오류는 예전 그대로 백오프 사다리를 탄다.
  갈림길은 "오류의 종류" 가 아니라 **"되돌릴 수 없는 것을 이미 했는가"** 다.
- **"정확히 한 번" 을 보장한다고 쓰지 않는다.** 원격이 확인해 주지 않는 이상 우리가 아는 것은
  "눌렀다는 사실" 뿐이다. 그래서 불확실을 **없애는** 대신 **보존해서 사람에게 넘긴다**.
- **이어가기는 승인이 아니다.** 재시작 뒤 이어가기는 언제나 새 구간을 시작하고, 위험 동작이면
  에이전트 가드가 **다시** 확인을 요구한다. 자격증명·보안 승인이 자동으로 나는 경로는 만들지 않았다.

## 3. 검증

### 3-1. 재현 → 수정 → 재확인 (순수 Node · 앱 없이 결정적)

| 무엇 | 수정 전 (재현) | 수정 후 |
|---|---|---|
| D1 클릭 시점의 장부 | 디스크에 **없음** (600ms 뒤 도착) | `persistEngageBoundary()` → `{ok:true}` + **두 파일 즉시 존재** |
| D1 재시작 후 중복 | 새 프로세스가 `alreadyDid === false` → **같은 글에 또 단다** | 새 프로세스가 `alreadyDid === true` → 건너뛴다 |
| D5 정상 한도 파일 로드 | `null` + `.corrupt-….bak` 격리 → 카운터 0 | 보존. 2회차 부팅에서 `comment:3` 유지, **4번째 댓글이 한도로 차단**, 손상본 0 |

D1 의 부정 대조는 **경계를 부르지 않고 `process.exit(0)` 으로 즉시 종료**해 재현했다 —
장부 파일 자체가 만들어지지 않았고, 새 프로세스는 그 글을 "안 건드린 것" 으로 봤다.

**D3 재현** — 같은 저장 파일을 수정 전/후 빌드에 각각 먹여 `initTaskRuntime()` 을 돌렸다:

| 저장돼 있던 작업 | 수정 전 (`dist-before-ir`) | 수정 후 |
|---|---|---|
| 🔐 로그인 대기 + `browser://settings#accounts` 버튼 | `재시작으로 중단됐습니다 — 이어서 진행할 수 있습니다.` · cause 없음 · **버튼 소실** | `🔐 로그인이 필요합니다 … (재시작으로 중단됨) 직접 처리한 뒤 이어가세요.` · `cause=login` · **버튼 유지** |
| `확인이 필요합니다: 클릭 "결제하기"` | **똑같은 한 줄** · cause 없음 | `확인이 필요합니다: 클릭 "결제하기" (재시작으로 중단됨) 이어가도 자동으로 승인되지 않습니다 — 다시 확인을 요청합니다.` · `cause=confirm` |
| 그냥 돌던 작업 | **똑같은 한 줄** | `재시작으로 중단됐습니다 — 이어서 진행할 수 있습니다.` (그대로 — 회귀 없음) |

수정 전에는 **세 작업이 화면에서 구분되지 않았다.** 돈을 쓰려다 멈춘 것과 그냥 멈춘 것이 같은 문장이었다.

### 3-2. 신규 상설 검사 — `verify-engage-durability` **6/6 PASS**

`npm run verify`(quick) 에 등록했다. 앱을 띄우지 않아 1초 안에 끝나므로 자주 볼수록 좋다.

| ID | 본 것 |
|---|---|
| ED1 | 경계 통과 직후(디바운스 대기 없이) 장부·한도가 디스크에 있다 |
| ED2 | 재시작을 넘어 중복이 막힌다 + **부정 대조로 수정 전 결함 재현** |
| ED3 | 한도 카운터가 재시작을 넘는다 (← **D5 를 잡아낸 검사**) |
| ED4 | 저장을 실제로 막으면 `{ok:false}` + **실제 파일명**이 담긴 사유 3종 |
| ED5 | `before-quit` 훅이 정확히 1개 등록되고 중복 등록되지 않는다 |
| ED6 | **양성 대조** — 다른 글·다른 행동·다른 계정은 막히지 않는다 |

ED6 가 없으면 ED2 는 "전부 막혀서" 통과한 것과 구분되지 않는다.

## 4. 알려진 한계 (정직하게)

- **`engageGuard` 가 없는 일반 작업**이 블로그에 댓글을 달면 이 장부의 보호를 받지 않는다.
  중복 방지는 참여 레시피(`buildBlogEngageTask`)로 만든 작업에만 걸린다 — 이번 범위 밖의 기존 설계다.
- `recordExternalWrite` 의 flush 가 실패하면 경고만 남긴다. 그 시점엔 클릭을 되돌릴 수단이 없고,
  막는 흉내만 내면 오히려 상태가 어긋난다. 같은 프로세스 안에서는 메모리 원장이 보호한다.
- **체크포인트(구간 진행요약)는 여전히 디바운스다.** 크래시로 마지막 구간의 진행요약을 잃으면
  이어가기가 그 구간의 **읽기**를 다시 한다. 되돌릴 수 없는 쪽은 원장이 막으므로 손실은 시간뿐이라
  동기 경계를 두지 않았다(재현된 피해가 없는 곳을 추측으로 고치지 않는다).
  덤으로, `recordExternalWrite` 의 flush 가 같은 파일을 쓰므로 **비가역 동작이 있을 때마다**
  체크포인트도 함께 확정된다.
- **원격이 확인해 주지 않는 "정확히 한 번" 은 여전히 불가능하다.** 우리가 보장하는 것은
  "모르는 채로 또 누르지 않는다" 까지다. 그래서 문서에도 그렇게만 적었다.
- **검증은 전부 로컬 픽스처다.** 실제 인스타그램·실제 블로그에서 돌리지 않았다(실계정·실게시 필요).
- **설치파일의 설치→부팅→제거는 시험하지 않았다.** 이 PC 에 사용자의 실설치본이 등록돼 있어
  무인 설치·제거가 그것을 덮어쓴다. **우회하지 않았다.** 설치 흐름의 정본 실증은 `rc.2` 까지다.
- **24시간 연속 실행은 실제로 돌리지 않았다**(가상 시계로만). 실제 시계 최장은 여전히 25.8분.
- **코드 서명 없음** — 사용자 제공 `.pfx` 가 필요하다.

## 5. 이번 라운드에 발견했으나 고치지 않은 것 (정직하게)

- **강제 종료 뒤 두 번째 탭이 세션 복원으로 살아나지 않는 경우**를 하네스 작업자가 실측했다
  (종료 직전 두 탭이 분명히 있었고 `last-stable.json` 과 대조까지 했다).
  이건 `task-runtime` 이 아니라 **세션/탭 복원 하위계통**(`session/index.ts`·`tab-service.ts`)의
  동작이고 이번 범위가 아니라 **손대지 않았다.** 하네스는 재부팅 후 같은 URL 로 탭을 다시 열어 우회했다.
  별도 라운드에서 볼 값어치가 있는 관찰이다.
- **`engageGuard` 없이 도는 일반 작업**의 댓글·좋아요는 여전히 장부 보호 밖이다(위 4절).
- `PUBLISH_RE` 의 `upload$` 갈래는 클릭 라벨에 대해 **여전히 닿지 않는다** — 알면서 뒀다(D6 참고).
