## 결함 ① — 저장 실패가 아무에게도 보이지 않았고, 그래서 게시가 그대로 나갔다

### 전

```ts
// json-store.ts
flush(): void { ... writeSyncAt(mySeq, text) }   // 실패해도 console.warn 뿐

// social-workflow.ts — startPublishTask
flushTasks()
store.flush()
startTask(pubTask.id)     // ← 두 flush 의 결과를 보지 않는다
```

`writeSyncAt` 은 실패 시 `false` 를 돌려주고 있었는데 `flush()` 가 그 값을 **버렸다**. 그래서
디스크가 꽉 찼거나 파일이 잠긴 순간에도 호출자는 아무것도 모른 채 되돌릴 수 없는 외부 쓰기를 시작했다.
그 뒤 앱이 죽으면 재시작한 제품에는 "무엇을 하려 했는가"(게시 작업)도 "어느 워크플로의 게시인가"도
남아 있지 않다 — 사용자는 글이 올라갔는지 스스로 확인해야 하고 이어갈 수도 없다.

바로 위 주석이 이 경계를 **말로는** 설명하고 있었다는 점이 이 결함의 성격을 보여 준다.
경계를 지키는 것은 주석이 아니라 반환값이다.

### 후

```ts
// json-store.ts — true = 쓸 것이 없었거나 착지 성공 / false = 직렬화·쓰기·rename 실패
flush(): boolean {
  if (seq <= persistedSeq) return true
  const text = serialize(); if (text === null) return false
  return writeSyncAt(mySeq, text)
}

// task-runtime.ts
export function flushTasks(): boolean { return store.flush() }

// social-workflow.ts
export function persistPublishBoundary(): { ok: boolean; failed: string[] } {
  const failed: string[] = []
  if (!flushTasks())  failed.push('작업 목록(ai-tasks.json)')
  if (!store.flush()) failed.push('게시 워크플로(ai-social.json)')
  return { ok: failed.length === 0, failed }
}

const saved = persistPublishBoundary()
if (!saved.ok) { abortPublishBeforeStart(wf, pubTask.id, saved.failed); return }
const started = startTask(pubTask.id)
if (!started.ok) abortPublishBeforeStart(wf, pubTask.id, [`게시 작업을 시작하지 못했습니다(...)`])
```

두 저장소를 **둘 다** 시도한다(첫 실패에서 멈추지 않는다) — 한쪽이라도 확정되면 그만큼은 남고,
사용자에게 **어느 쪽이 막혔는지** 정확히 말할 수 있다.

### 물러날 때 고아를 남기지 않는다

`abortPublishBeforeStart` 의 순서가 핵심이다. 두 저장소 중 **작업 쪽만** 성공했으면 디스크에는
시작되지 않은 `queued` 게시 작업이 남는다 — 재시작 후 사용자가 작업 UI 에서 그것을 직접 시작하면
그게 곧 경계를 우회한 게시다. 그래서

1. **먼저** `setResumeBlock(...)` 으로 차단 이유를 붙이고 `flushTasks()` 로 확정한다
   (`startTask`·`resumeTask` 둘 다 `resumeBlockedReason` 을 보므로, 뒤이은 삭제가 디스크에 못 닿아도
   남는 것은 '시작할 수 없는 작업'이다),
2. 그다음 `deleteTask` + `flushTasks()`.

그리고 단계를 **`failed` 가 아니라 `review` 로** 되돌린다 — 저장 문제를 고친 뒤 같은 이미지·같은
캡션으로 다시 "게시"를 누르면 그대로 이어진다. 자동 게시는 다시 시도하지 않는다(선승인 소비 기록이
이미 남아 `autoPublishVerdict` 가 거부한다 — **자동 재시도 없음**).

## 결함 ② — 모델이 "게시됐다"고 **말한 것**을 게시됐다는 **근거**로 썼다

### 전

```ts
const marker = parseVerifyMarker(v.result ?? '')     // `게시됨:` / `게시안됨:` 표지만 본다
if (marker === 'published')      { wf.stage = 'done'; ... }                  // 완료 확정
if (marker === 'not-published')  { setResumeBlock(pubTaskId, null); ... }    // 차단 자동 해제
```

그 한 줄은 페이지를 한 번도 보지 않아도, 로그인 화면에서도, 엉뚱한 계정에서도, 목록이 끝까지 안
불러와졌어도 나온다. 그런데 결과는 되돌릴 수 없다 — `게시됨` 을 잘못 믿으면 **안 올라간 글이
'완료'로 닫히고**, `게시안됨` 을 잘못 믿으면 차단이 풀려 **같은 글이 두 번 올라간다**.

### 후 — 모델이 만들 수 없는 값과 대조한다

모델의 산문은 **결론의 형식**으로만 쓰고, 결론을 **런타임이 실제로 관찰한 사실**과 대조한다.

| 층 | 무엇 |
|---|---|
| `agent-gate.ts` | `[게시 확인]` 표식(`buildVerifyProbeMark`/`parseVerifyProbeMark`), 화면 대조(`matchVerifyProbe`), 근거 유효성(`sightingSupportsPublication`) — 전부 순수 함수 |
| `agent.ts` | **읽기 전용 작업**에서만, 관찰 텍스트·주소에서 직접 뽑아 `sighting` 이벤트를 낸다. 지시성 문구가 있는 페이지는 근거로 세지 않는다 |
| `task-runtime.ts` | `PersistentTask.readSightings[]`(url·host·needle·snippet·at)로 **작업에 영속**. 손상 파일은 모양이 맞는 항목만 통과 |
| `social-workflow.ts` | 표지 + 근거를 **함께** 봐야 결론을 낸다 |

읽기 전용으로 제한한 이유는 명확하다 — 게시 작업은 캡션을 직접 **입력**하므로 그 화면 텍스트에
캡션이 들어 있는 것이 당연하다. 그것을 "올라간 증거"로 세면 입력만 하고도 게시됐다고 믿게 된다.

### 판정

| 모델의 표지 | 화면 근거 | 결론 |
|---|---|---|
| `게시됨:` | 같은 사이트·같은 캡션·이번 확인 이후 | **완료 확정** — 영수증에 출처 주소와 발췌를 남긴다 |
| `게시됨:` | 없음 / 다른 사이트 / 다른 캡션 / 오래됨 | **불확실 유지** — 왜 인정되지 않았는지 이유까지 보인다 |
| `게시안됨:` | — | **불확실 유지**(자동 해제 없음) |
| 표지 없음 | — | **불확실 유지** |

### 비대칭은 의도된 것이다

**있는 것은 볼 수 있지만 없는 것은 증명할 수 없다.** 목록에서 캡션을 봤다면 올라갔다는 구체적
증거가 된다. 못 봤다면 아직 반영이 안 됐거나·다른 계정 화면이거나·목록이 잘렸을 수 있다 —
증거가 아니다. 그래서 `게시안됨` 은 **자동으로 차단을 풀지 않는다**. 사람이 직접 확인해
"게시 안 됨 · 이어가기"를 누르는 길은 그대로 남아 있다(그 버튼은 예전과 같다).

### 고치는 길에 드러난 세 가지 (같은 결함의 이웃)

**① 확인이 도중에 끊기면 워크플로가 영원히 멈췄다.** `reconcileVerifyTask` 가 `interrupted` 를
"아직 진행 중" 으로 묶어 두었는데, `task-runtime` 은 설계상 **부팅만으로 재개하지 않는다** —
즉 그 상태는 끝난 것도 도는 것도 아니었다. 화면에는 "🔎 확인하는 중…" 만 뜨고 확인 버튼은
비활성이라(`disabled={!!w.verifyTaskId}`) 사용자가 빠져나올 길이 없었다. 확인은 **읽기 전용**이라
중간에 끊겨도 잃을 것이 없으므로, 자리를 놓아주고 다시 누를 수 있게 했다.

**② 차단을 푸는 행위가 스스로 차단을 되살렸다 (하네스가 새로 잡은 결함).** 사용자가 "게시 안 됨 ·
이어가기"를 눌러 `resolvePublishUncertainty('not-published')` 가 `setResumeBlock(pubTaskId, null)` 을
부르면, 그 함수가 `emitChanged()` → `taskEvents 'changed'` → `reconcileAll` → `reconcilePublish` 를
**같은 호흡에서** 부른다. 그 시점에도 게시 작업은 아직 `interrupted` 이라 `markPublishUncertain` 이
방금 푼 차단을 즉시 다시 걸었다. 응답은 `ok:true` 인데 화면은 그대로다 — **안전 장치의 유일한
탈출구가 막혀 있었다.** 이번 라운드가 만든 것이 아니라 원래 있던 결함이고, 새로 쓴 검사
(R3-VER-NOTPUB)가 처음 드러냈다.

고침: `ImagePostWorkflow.uncertaintyResolvedFor`(사람이 결론 낸 게시 작업 id)를 `setResumeBlock`
**보다 먼저** 기록하고, `markPublishUncertain` 이 그 작업에 한해 다시 표시하지 않는다. 그 작업이
**실제로 다시 돌기 시작하면** 표시를 지워, 그 뒤의 중단은 새로운 불확실로 다시 묻는다(재시작을
넘겨 유지되도록 로드 복원에도 넣었다).

**③ 관찰 본문 1800자 상한 때문에 진짜 게시물을 놓칠 수 있었다.** 계정 첫 화면의 메뉴·안내가 길면
실제 글이 그 뒤로 밀린다. 그러면 "근거 없음" 이 되는데, 그건 안전한 방향이긴 해도 **정확하지 않다**
(사용자가 매번 직접 확인해야 한다). 그래서 **같은 사이트이고 본문이 잘렸을 때만** 전체 본문을 한 번
더 훑는다(`probeFullTextForNeedles`). 돌려받는 것은 찾았는가와 짧은 발췌뿐이라 **프롬프트는 커지지
않는다** — 모델에게 본문 전체를 보내지 않는다.
