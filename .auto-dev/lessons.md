# ezBrowser — 교훈

<!-- 교훈 목록 (자동 관리, 최신이 아래) -->
- **음성 대조는 "결함을 넣으면 빨개지는가" 를 넘어 "옛 판정은 놓치고 새 판정만 잡는가" 까지 봐야 한다.**
  X13 강화의 경우 제품 결함(탭 미등록) 주입은 옛·새 판정이 **둘 다** 실패해 강화의 가치를 증명하지 못한다.
  판정을 함수로 뽑아(`judgeX13`) 같은 함수에 결함 데이터를 먹이면, 제품으로는 만들 수 없는 조건
  (라이브러리가 세션 불일치 addTab 에 TypeError 를 던져 교차 등록 자체가 불가)까지 검출력을 확인할 수 있다.
  단 이것은 **판정식의 검증**이지 제품 검증이 아니므로, 제품 결함 주입과 **둘 다** 돌리고 그렇게 적을 것.
- **제품을 일부러 망가뜨렸다면 복구는 소스가 아니라 컴파일 산출물에서 확인한다.**
  `git diff` 가 깨끗해도 `app/dist/main/*.js` 와 `app.asar` 가 낡아 있으면 다음 실행은 망가진 앱을 잰다
  (V5 의 "낡은 결과 파일" 과 같은 부류). 산출물 타임스탬프가 소스보다 뒤인지까지 볼 것.
- **"우리 코드 밖이라 못 고친다" 로 멈추지 말고 엔진 소스와 릴리스 브랜치까지 가라.**
  X15 는 두 라운드 동안 "라이브러리에 구현이 없다" 에서 멈춰 GAP 이었다. Electron 소스를 직접 읽자
  `CanAccessTarget` 이 `browser_context` 인자를 **받아 놓고 안 쓰는** 것이 드러났고(원인 확정),
  커밋 이력을 훑자 upstream 이 이미 고쳐(PR #50906) **Electron 39 부터 들어 있음**이 나왔다.
  결론이 "포크 필요"(사실상 영구 GAP)에서 **"판올림 여부 결정"**(실행 가능한 선택지)으로 바뀐다.
  `gh api repos/<o>/<r>/commits?path=<파일>` + 릴리스 브랜치별 파일 대조 두 번이면 된다.
- **"막혔다" 를 확인할 때는 대상 목록을 먼저 뜨라 — 예상 밖의 대상이 거기 있다.**
  X25 는 시크릿 탭만 물었는데, id→페이지 매핑을 찍자 **외피(브라우저 UI) 자체가 `file://` 로 로드되는
  또 하나의 webContents** 로 잡혀 있었고, 확장이 거기서 시크릿 창의 주소창 값을 실제로 읽어 갔다(X26).
  "무엇이 안 뚫렸나" 만 보면 놓치고, "무엇에 닿을 수 있나" 를 열거하면 보인다.

- **제품이 쓸 만한지는 기능 하네스로는 보이지 않는다.** "설명 없이 연결되는가" 는 첫 사용자의 여정을
  그대로 따라가야만 드러난다. 이번에 AI 첫 사용이 막다른 길이었는데, 기존 하네스 32종은 **전부 초록인 채로**
  몇 달을 지나왔다(그 하네스들은 "기능이 규격대로 도는가" 만 본다).
  진단 하네스(`build/audit-firstrun-cdp.mjs`)는 PASS/FAIL 이 아니라 **관찰**이므로 게이트에 넣지 않되,
  거기서 찾은 결함은 정식 검사(`verify-ai-connect`)로 **승격해 게이트에 등록**한다.
- **UI 전환까지 보려면 IPC 를 직접 부르지 말고 화면의 버튼을 눌러야 한다.** 처음에 `connectProvider` 를
  IPC 로 직접 불러 "연결 성공" 은 확인했지만 패널이 안 바뀌는 것을 놓칠 뻔했다(그 자리에 실제 제품 결함이 있었다 —
  `settings.onChange` 미구독). 사용자가 누르는 경로 그대로 검증해야 그 사이의 결함이 보인다.
- **"뒤로가 동작하는가" 를 이력이 하나뿐인 탭에서 검사하면 거짓 FAIL 이 난다** — 그 탭에서 뒤로가
  아무 일도 안 하는 것이 정상이다. 상태를 먼저 만들고 검사할 것.
- **"브라우저 구조상 불가"라고 쓰기 전에 그 제약이 **누구에게** 걸리는지 확인하라.** 같은 출처 정책(SOP)은
  *페이지 안의 JS* 가 다른 출처 문서를 읽는 것을 막는 규칙이지, *브라우저 자신*이 자기 프레임에 접근하는 것을
  막는 규칙이 아니다. 두 라운드 동안 "cross-origin iframe 은 접근 불가(구조적 한계)"로 적고 그것을 **검사의
  합격 조건으로까지 굳혀** 놨는데(U1), 실제로는 Electron `WebFrameMain.executeJavaScript` 한 줄이면 된다.
  렌더러 권한을 완화하지 않고(webSecurity·sandbox 불변) 메인 프로세스 권한만 쓴다.
- **프레임 안에서 `scrollIntoView` 를 부르면 부모 문서까지 따라 스크롤된다.** 그래서 행동 시작 시 계산해 둔
  프레임 오프셋은 클릭 직전에 이미 낡는다 — 그 값으로 누르면 **"눌렀다"고 성공 보고하면서 엉뚱한 자리를**
  누른다(F8 이 실측으로 잡았다). 좌표는 **스크롤을 유발한 뒤에 다시 재라.**
- **cross-origin iframe(OOPIF)은 `/json/list` 에도 부모 JS 에도 안 잡힌다** — 하네스가 프레임 안 상태를
  확인하려면 fixture 가 `postMessage` 로 부모에 보고하게 하는 게 가장 단순하고 확실하다. 이걸 모르고
  `childSession()` 을 만들었다가 6개 검사가 한꺼번에 거짓 FAIL 로 나왔다.
- **조용한 실패는 "실패"가 아니라 "엉뚱한 성공"으로 나타난다.** `pressKey` 는 ref 검증 실패를 삼키고 키를
  지금 포커스로 보내면서 `ok:true` 를 돌려줬다 — Ctrl+A·Delete·Enter 가 의도하지 않은 칸에 간다.
  **대상을 지정한 동작은 대상을 못 찾으면 아무 것도 하지 말고 실패해야 한다**(fail-closed).
- **막힌 화면 감지는 "본문에 그 단어가 있는가"로 하면 안 된다.** 안내문서·약관에 '로그인'·'verify'·'인증'은
  흔하다. 구조적 신호(보이는 password 칸, 실제 CAPTCHA 위젯)만 쓰고, 문구는 "본문이 아주 짧은 차단 간지"
  라는 구조적 조건과 함께일 때만 보조로 쓴다. 오탐 대조군(C4)을 반드시 같이 둘 것.
- **"안 보였다" 를 "없었다" 로 세면 검사가 조용히 빈 껍데기가 된다.** SL17 은 교차 출처 iframe 을
  **읽지 못한 것**을 "비어 있음" 으로 세고 있었다 — 제품이 통째로 깨져도 똑같이 통과한다.
  판정에 **읽었다는 사실 자체**(+ 읽은 문서의 주소)를 넣어야 한다. 강화 직후 FAIL 이 난 것이
  1차 성과였다: 검사가 스스로 "나는 아무것도 못 봤다" 고 말하게 만드는 것이 먼저다.
- **공유 라이브러리의 콜백 시그니처는 추측하지 말고 소스에서 확인하라.** `build/lib/cdp.mjs` 의
  이벤트 구독자는 `(_, method, params, sessionId)` 로 불리는데 `(msg) => msg.method` 로 쓰면
  **예외 없이 아무 이벤트도 안 잡힌다**. 위 빈 검사의 근본 원인이 이것이었다.
- **교차 출처 프레임을 CDP 로 읽는 경로는 하나가 아니다** — 같은 렌더러면
  `Page.createIsolatedWorld(frameId)`, 별도 프로세스(OOPIF)면 `Target.setAutoAttach(flatten)` 의
  자식 세션. 한 경로만 시도하고 실패를 "없음" 으로 해석하지 말 것.
