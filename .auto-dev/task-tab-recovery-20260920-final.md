## 1. 고친 것 (사용자가 보는 동작)

### ① 복원을 넘어 "바로 그 탭" 을 확정한다

창·탭 id(`win-N`/`tab-N`)는 **프로세스마다 1부터 다시 발급**된다. 그래서 크래시 복원 뒤의 `tab-3` 은
종료 전의 `tab-3` 과 아무 관계가 없다. 내구 자동화 작업은 예전에 `checkpoint.windowId` + **URL 호스트
스캔**으로 대상을 되찾았고, 같은 사이트 탭이 여러 개면 **엉뚱한 탭**(다른 창·다른 계정 세션)을 집을 수
있었다. 발행·결제 작업이면 사고다.

- `TabRecord.restoreKey` / `BrowserWindowContext.restoreKey` — 재사용되지 않는 **복원 안정 키**.
  세션 스냅샷에 함께 저장하고 복원 시 **그대로 물려준다**(`tab-service.ts`·`window-service.ts`·
  `session/index.ts`·`snapshot-schema.ts`).
- `task-runtime.ts` 의 `resolveTaskTab` 이 **키로만** 찾는다. **호스트 스캔 폴백은 삭제했다.**
  키로 찾은 탭이 잠들어 있으면(복원 탭은 대개 `about:blank`) 깨우고 로드를 기다린다.
  같은 사이트 안의 리다이렉트는 흡수하고, 호스트까지 다르면 쓰기 작업은 진행하지 않는다.
- 못 찾으면 **막다른 길 대신** `waitCause: 'tab-target'` 으로 멈추고 사람에게 묻는다.

### ② "어느 탭에서 이어갈지" 를 사람이 고른다 (신규 UI)

- 메인: `listTaskTargets` / `setTaskTarget` (IPC `ai:ptask-targets` / `ai:ptask-set-target`).
  후보 목록은 **메인이 정본**이고, `setTaskTarget` 은 렌더러가 준 tabId 를 **다시 검증**한다
  (목록에 있는가 · 시크릿 경계 · 그 사이 닫히지 않았는가).
- 외피: 작업 카드 안에서 펼쳐지는 인라인 패널(`.ai-target-picker`). 떠 있는 팝오버로 만들지 않았다
  (사이드바 도크 규칙 — 콘텐츠 뷰를 가린다).
- **고르는 것은 실행도 승인도 아니다.** 고르면 `interrupted` 로 돌아갈 뿐이고 이어가기는 따로 눌러야 하며,
  `resumeBlockedReason`·발행 불확실 관문·위험 동작 확인은 **그대로 남는다**.
- 'tab-target' 일 때 일반 승인/거부 UI 는 **의도적으로 감춘다** — `confirmTask` 로는 풀리지 않는
  대기라서 버튼이 있으면 눌러도 아무 일이 없어 사용자를 헷갈리게 한다.

### ③ 게시 단계의 같은 결함 (범위 밖에서 발견 → 고쳤다)

`social-workflow.ts` 의 `preparePublishTab` 이 저장된 `params.tabId` 를 **그대로 믿고** `loadURL` 했다.
재시작 뒤 그 id 는 무관한 복원 탭을 가리킬 수 있고, 그 탭이 **다른 워크스페이스**면
**로그인한 계정이 조용히 바뀐 채로 게시**된다. 이제 생성 작업 체크포인트의 `tabKey` 로 대상을 확정하고,
키가 없는 옛 기록만 raw id 를 쓰되 **워크스페이스가 같은지** 확인한다(다르면 같은 세션에 새 탭을 연다).

## 2. 재현 (막연한 주장이 아니라 수치)

`build/verify-auto-publish.mjs`(순수 Node · quick 게이트 상설)에 시나리오 4종을 신설했다.
판정은 **우리 코드가 실제로 부른 `loadURL` 기록**으로 한다.

| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| 재시작 뒤 그 id 가 **다른 세션의 탭**이 돼 있다 | **FAIL** — `{"tabId":"tab-1","url":"https://www.instagram.com/"}` (남의 탭을 게시 사이트로 끌고 감) | PASS — 그 탭 건드림 0회 |
| 대신 원래 세션에 새 탭을 열어 잇는다 | **FAIL** — `tabId: "tab-1"` | PASS — `created:true`, `tab-new` |
| 복원 안정 키로 찾은 탭에서 잇는다(id 가 달라져도) | **FAIL** — 키를 무시하고 `tab-1` | PASS — `tab-7` |
| 키가 없어도 **다른 세션**의 탭이면 쓰지 않는다 | **FAIL** — `tab-1` 사용 | PASS — `tab-new` |
| (하위호환) 키 없는 옛 기록 + 같은 세션 | PASS | PASS — 회귀 없음 |

**음성 대조 방법**: 컴파일 산출물(`app/dist/.../social-workflow.js`)의 대상 선택부를 수정 전 코드
(`let tabId = wf.params.tabId`)로 되돌려 실행 → **4 FAIL** 확인 → 원복 후 **58/58 PASS** 재확인.
(제품을 일부러 망가뜨렸을 때 복구 확인은 소스가 아니라 **컴파일 산출물**에서 했다.)

### 통합 중 팀장이 막은 구멍 2건

1. **`setTaskTarget` 이 아무 대기에나 먹혔다** — 결제 승인(`agent-confirm`)·발행 불확실(`ledger`)을
   기다리던 작업에서도 대상 선택이 통과해 ① 기다리던 에이전트가 영영 응답을 못 받고 ② `waitCause` 가
   지워져 "무엇을 기다리다 멈췄는지" 신호가 사라졌다. → `tab-target` 대기에서만 받아들인다(W9 가 회귀 검사).
2. **취소·일시정지가 부작용 뒤에야 반영되는 새 경합** — `resolveTaskTab` 이 async 가 되면서(잠든 탭을
   최대 15초 깨운다) 그 사이 누른 중단이 유실되고 12단계 구간이 그대로 실행될 수 있었다. 이 시점엔
   아직 `reqId` 가 없어 `cancelAgentTask` 로도 못 막는다. → 재바인딩 직후에 **부작용 직전 관문**을
   하나 더 두고, 깨우기 대기도 상태가 바뀌면 즉시 끊는다. (코드 리뷰가 잡아 준 것이다.)
